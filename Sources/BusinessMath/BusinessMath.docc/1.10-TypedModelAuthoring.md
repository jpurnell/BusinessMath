# Typed Model Authoring

Write a model the compiler can check, in a vocabulary that says what your numbers mean.

## Overview

<doc:1.9-FormulaEvaluation> makes a model's arithmetic into data. That is what allows one
codebase to handle two companies whose accountants made different calls, and it is what lets a
spreadsheet be read into a model at all — a formula is a string, so it can come from anywhere.

The cost is that a string says nothing. `"revenue * margin"` and `"revenue + margin"` are equally
valid strings, and only one of them means anything. So is `"revenu * margin"`, which means
nothing at all and will tell you so at runtime, in whatever period the evaluator reaches first.

This layer adds a second way to write the same model, where those mistakes are compile errors.
Nothing beneath it changes: a typed model **is** a `ModelDefinition`, evaluated by the same
engine, producing the same numbers. It is a spelling, not a second implementation.

```swift
let years = [Period.year(2024), Period.year(2025)]
let figures: [String: TimeSeries<Double>] = [
    "Revenue": TimeSeries(periods: years, values: [1_000, 1_150]),
    "EBITDA margin": TimeSeries(periods: years, values: [0.4, 0.4]),
]

let revenue = LineItem<Money>("Revenue")
let margin  = LineItem<Ratio>("EBITDA margin")
let ebitda  = LineItem<Money>("EBITDA")

let model = ModelDefinition<Double>(inputs: figures)
    .defining(ebitda, as: revenue.expr * margin.expr)
```

`revenue.expr + margin.expr` does not compile. Neither does `revenu.expr`, because `revenu` is
not a variable that exists.

## The four units

A ``ModelUnit`` is a *phantom* type. It exists to be checked, is never instantiated, holds no
storage, and costs nothing at runtime — the entire mechanism runs before your model is built and
leaves no trace in it.

| Unit | What it measures | Examples |
|---|---|---|
| ``Money`` | A currency amount | Revenue, a balance, a cash flow |
| ``Rate`` | A proportion **per period** | Interest rate, growth, a coupon |
| ``Ratio`` | A dimensionless proportion | A margin, a multiple, a share |
| ``Count`` | A count of periods, units, or shares | Years to exit, shares outstanding |

The distinction between ``Rate`` and ``Ratio`` is the one that earns its keep. Both are printed
as percentages and both are stored as `0.1`, but a rate is *per period* and a margin is not.
Only a rate can be applied over the wrong timeline, and that is the error this layer exists to
catch.

## Line items and expressions

A ``LineItem`` is the name your model knows an account by, held in a Swift value:

```swift
let openingDebt  = LineItem<Money>("Opening Debt")
let interestRate = LineItem<Rate>("Interest Rate", basis: .annual)
```

The name is still a string in the model — that is what keeps a model serializable and what lets
an importer target it. What changed is that *your* reference to it is a value the compiler holds,
so a typo does not compile and rename works across a project.

``LineItem/expr`` turns an item into an ``Expr``, and expressions compose:

```swift
let interest = openingDebt.expr * interestRate.expr   // Expr<Money>
```

An `Expr` renders a formula string in the grammar <doc:1.9-FormulaEvaluation> already reads.
You can look at it — `interest.formula` is `"([Opening Debt] * [Interest Rate])"` — which is
often the quickest way to satisfy yourself that the typed form and the string form are the same
model.

### The algebra

Legal combinations have an overload. Illegal ones simply have none, so they fail to compile.

| Combination | Result | Why |
|---|---|---|
| `Money + Money` | `Money` | Amounts add |
| `Money − Money` | `Money` | Amounts subtract |
| `Money * Ratio` | `Money` | Scaling by a proportion |
| `Money * Rate` | `Money` | Applying a per-period rate |
| `Ratio * Ratio` | `Ratio` | Composing proportions |
| `Money / Money` | `Ratio` | A margin |
| `Money / Count` | `Money` | An amount per unit |
| `Money / Ratio` | `Money` | Grossing up |

And the ones with no overload at all:

| Written | Why there is no such thing |
|---|---|
| `Money + Ratio` | 1,000 dollars plus 40% is not a quantity |
| `Money * Money` | Money squared is not something a statement holds |
| `Rate + Money` | A rate and an amount are different dimensions |
| `Money * 0.4` | A bare literal has no unit — see below |

### Literals name their own unit

There is no `ExpressibleByFloatLiteral`. A bare `0.4` would take its unit from context, which is
exactly the ambiguity the units exist to remove:

```swift
revenue.expr * ratio(0.4)              // a margin
revenue.expr * rate(0.4, per: .annual) // a growth rate
```

Three characters longer, and it says which `0.4` you meant. It also keeps compilation fast: the
type checker never has to infer a literal's type across an overload set, which is the case it is
slowest at.

### The growth factor

`Revenue × (1 + g)` is the commonest line in financial modelling, and it cannot be written
directly:

```swift
let growth = LineItem<Rate>("Revenue growth", basis: .annual)
```

<!-- docs:illustrative -->
```swift
revenue.expr * (ratio(1.0) + growth.expr)   // does not compile
```

That refusal is correct — a dimensionless `1` and a per-period rate are not the same dimension —
but the idiom is too common to leave unavailable. Use ``factor(_:)``, which means *one plus this
rate*:

```swift
revenue.expr * factor(growth.expr)          // Expr<Money>
```

Naming it is a small gain over `1 + g`: a growth factor is a distinct quantity from the rate it
is built from, and now it says so.

## The checks a compiler cannot make

The algebra rejects what is wrong for *any* model. Some errors depend on the model, and only
appear once one exists. ``ModelDefinition/validateUnits()`` finds those.

```swift
try model.validateUnits()
```

**Conflicting units.** One name cannot be two things:

```swift
let debtAmount = LineItem<Money>("Debt")   // a balance, in dollars
let debtShare  = LineItem<Ratio>("Debt")   // 60% of the purchase price
```

Both are well-typed. Used in one model they are one account with two meanings, and whichever
declaration a reference resolves to decides the answer. This throws
``TypedModelError/conflictingUnits(name:_:_:)``.

**A rate with no basis.** A ``Rate`` whose `basis` is `nil` cannot be checked against anything,
so the most valuable check in this family becomes unavailable. This throws
``TypedModelError/missingRateBasis(account:)``.

**A rate on the wrong timeline.** This is the one worth the whole layer:

```swift
let months = (1...12).map { Period.month(year: 2024, month: $0) }
let monthlyFigures: [String: TimeSeries<Double>] = [
    "Balance": TimeSeries(periods: months, values: Array(repeating: 100, count: 12))
]

let balance = LineItem<Money>("Balance")
let monthlyInterest = LineItem<Money>("Interest")
let annualRate = LineItem<Rate>("Interest Rate", basis: .annual)

let monthlyModel = ModelDefinition<Double>(inputs: monthlyFigures)
    .defining(monthlyInterest, as: balance.expr * annualRate.expr)

do {
    try monthlyModel.validateUnits()
} catch TypedModelError.rateBasisMismatch(let account, let declared, let applied) {
    print("\(account) is per \(declared) but the model runs \(applied)")
    // Interest Rate is per annual but the model runs monthly
}
```

An annual rate on a monthly timeline is off by twelve. It evaluates without complaint, and the
result looks entirely plausible in a report. If the conversion is deliberate, declare the rate at
the timeline's basis — saying so is the point, because a converted rate and an unconverted one
are indistinguishable once both are just numbers.

The timeline is read from the model's inputs rather than declared, because it is a fact about the
figures you supplied. A model with no data yet has no timeline, so the check is skipped rather
than guessed.

### What validation cannot see

Only what the typed API declared. A model written entirely with strings declares nothing, so
`validateUnits()` succeeds without checking anything:

```swift
let untyped = ModelDefinition<Double>().defining("EBITDA", as: "Revenue * 0.4")
try untyped.validateUnits()          // succeeds
untyped.unitDeclarations.isEmpty     // true — nothing was known
```

A clean validation of an untyped model means nothing was known, not that nothing is wrong. Read
``ModelDefinition/unitDeclarations`` when you want to know how much was checked.

## A worked example: a cash sweep

Interest accrues on an opening balance, a sweep repays what cash allows, and the balance closes
lower by what was swept.

```swift
let sweepFcf          = LineItem<Money>("Free Cash Flow")
let sweepOpeningDebt  = LineItem<Money>("Opening Debt")
let sweepInterestRate = LineItem<Rate>("Interest Rate", basis: .annual)
let sweepInterest     = LineItem<Money>("Interest")
let sweepPaydown      = LineItem<Money>("Sweep")
let sweepClosingDebt  = LineItem<Money>("Closing Debt")

let sweepYears = [Period.year(2024), Period.year(2025), Period.year(2026)]
let sweepFigures: [String: TimeSeries<Double>] = [
    "Free Cash Flow": TimeSeries(periods: sweepYears, values: [30, 30, 30]),
    "Opening Debt": TimeSeries(periods: sweepYears, values: [100, 70, 40]),
    "Interest Rate": TimeSeries(periods: sweepYears, values: [0.1, 0.1, 0.1]),
]

let sweepModel = ModelDefinition<Double>(inputs: sweepFigures)
    .defining(sweepInterest,    as: sweepOpeningDebt.expr * sweepInterestRate.expr)
    .defining(sweepPaydown,     as: min(sweepFcf.expr, sweepOpeningDebt.expr))
    .defining(sweepClosingDebt, as: sweepOpeningDebt.expr - sweepPaydown.expr)

try sweepModel.validateUnits()
let sweepResults = try sweepModel.solve()

let debt = sweepModel.series(for: sweepClosingDebt, in: sweepResults)
```

Three things are worth noticing.

``min(_:_:)`` and ``max(_:_:)`` keep the unit they are given, so `min(sweepFcf, sweepOpeningDebt)` is
money and `min(sweepFcf, margin)` does not compile.

This particular sweep is acyclic: interest accrues on the opening balance, which is an input.
Accrue it on the *average* of opening and closing instead and the model becomes genuinely
circular — closing depends on the sweep, the sweep on what is left after interest, and interest
on closing. Nothing in the typed layer has to say so. Cycle resolution is ``ModelDefinition``'s,
unchanged, and the typed spelling reaches it the same way the string one does. See
<doc:1.9-FormulaEvaluation>.

``ModelDefinition/series(for:in:)`` is where a typed model stops being typed. What comes back is
plain numbers, because a unit is a claim about what a number *means*, not a property of the
number itself.

## Carrying a balance between periods

A formula here is **period-local**: it never reaches into another period. A balance moves forward
because a ``Rollforward`` says it does, in data:

```swift
let driver = PeriodDriver(
    definition: sweepModel,
    rollforwards: [Rollforward(opening: "Opening Debt", closing: "Closing Debt", seed: 100)]
)
let carried = try driver.run(over: sweepYears)
```

The split matters: **within-period circularity is solved by iteration, cross-period carry is
data.** Mixing them produces a model that either fails to converge or quietly reports every
figure one period early.

## When not to use this

The string API is not deprecated and is not going anywhere. Reach for it when:

- **A formula comes from outside your source.** A spreadsheet importer, a configuration file, or
  a user — none of them can hand you a Swift value.
- **The model is assembled dynamically.** If account names are computed, a typed handle buys
  nothing that a string does not.
- **You are exploring.** Strings are quicker to type at a REPL.

The two mix freely in one model. Typed definitions get checked; string ones do not, and
``ModelDefinition/unitDeclarations`` tells you which is which.
