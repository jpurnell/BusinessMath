# Debugging Financial Models

Diagnose and fix issues in financial models effectively with comprehensive debugging tools.

## Overview

BusinessMath provides powerful debugging and diagnostic tools to help you trace calculations, validate models, and profile performance. These tools are essential for understanding complex financial models and ensuring accuracy.

This guide shows you how to:
- Use ``ModelDebugger`` to trace calculations and inspect model state
- Profile performance with ``ModelProfiler``
- Validate model integrity
- Diagnose common issues
- Optimize model performance

## Why Debugging Tools Matter

Financial models can be complex, with:
- **Dependencies between accounts** that constrain the order of evaluation
- **Missing data** that breaks calculations
- **Performance bottlenecks** in large models
- **Unexpected results** from formula errors

The right debugging tools help you:
- Trace calculation flows to understand results
- Identify performance problems before they impact production
- Validate model correctness automatically
- Catch errors early in development

## ModelDebugger: Inspection and Validation

### Basic Usage

The ``ModelDebugger`` provides real-time inspection of financial models:

```swift
import BusinessMath

// Create a financial model
let company = Entity(id: "ACME", primaryType: .ticker, name: "Acme Corp")
let q1 = Period.quarter(year: 2025, quarter: 1)
let periods = [q1, q1 + 1, q1 + 2, q1 + 3]

let model = buildModel(for: company) {
    Revenue("Product Sales", periods: periods, values: [100_000, 110_000, 120_000, 130_000])
    Expense("COGS", periods: periods, values: [60_000, 66_000, 72_000, 78_000], type: .costOfGoodsSold)
    Expense("OpEx", periods: periods, values: [20_000, 20_000, 20_000, 20_000], type: .operatingExpense)
}

// Every report in this guide stamps the moment it was generated, and every profile reports
// a measured duration. Both would make the output below different on your machine and on
// mine, so the examples inject two instruments: a clock stopped at a chosen instant, and a
// monotonic counter that moves only when the example tells it to. Omit both arguments in
// your own code — the defaults are the real clock and the real elapsed time.
let docsClock = FixedWallClock(at: Date(timeIntervalSince1970: 1_767_225_600))  // 2026-01-01T00:00:00Z
let docsElapsed = ManualElapsedTimeSource()

// Create debugger and inspect model
let debugger = ModelDebugger(clock: docsClock, elapsedTime: docsElapsed)
let snapshot = await debugger.snapshot(of: model)

print(snapshot.summary)
// Model: Acme Corp
// Accounts: 3 (1 revenue, 2 expenses)
// Periods: 4 quarters
// Status: Valid
```

### Detailed Model Inspection

Inspect specific aspects of your model:

```swift
// Get detailed snapshot
let inspectionDebugger = ModelDebugger(clock: docsClock, elapsedTime: docsElapsed)
let inspectionSnapshot = await inspectionDebugger.snapshot(of: model)

// Inspect accounts
print("Revenue Accounts:")
for account in inspectionSnapshot.revenueAccounts {
	print("  \(account.name): \(account.total.currency(0))")
}

print("\nExpense Accounts:")
for account in inspectionSnapshot.expenseAccounts {
	print("  \(account.name): \(account.total.currency(0))")
	if let expenseType = account.expenseType {
		print("    Type: \(expenseType)")
	}
}

// Inspect periods
print("\nPeriod Analysis:")
for period in inspectionSnapshot.periods {
	let revenue = model.totalRevenue(for: period)
	let expenses = model.totalExpenses(for: period)
	let netIncome = revenue - expenses

	print("\(period.label):")
	print("  Revenue: \(revenue.currency(0))")
	print("  Expenses: \(expenses.currency(0))")
	print("  Net Income: \(netIncome.currency(0))")
}
```

### Calculation Tracing

Trace how values are calculated:

```swift
let tracingDebugger = ModelDebugger(clock: docsClock, elapsedTime: docsElapsed)

// Enable tracing
await tracingDebugger.enableTracing()

// Perform calculations
let q1Revenue = model.totalRevenue(for: q1)

// Get calculation trace
let trace = await tracingDebugger.getTrace()

print("Calculation Trace for Q1 Revenue:")
for step in trace.steps {
    print("\(step.operation): \(step.input) → \(step.output)")
}

// Example output:
// GetAccount(Product Sales): Period(2025-Q1) → 100,000
// Sum(Revenue Accounts): [100,000] → 100,000
```

### Validation Reports

Validate model integrity:

```swift
let validationDebugger = ModelDebugger(clock: docsClock, elapsedTime: docsElapsed)
let validation = await validationDebugger.validate(model)

if validation.isValid {
	print("✅ Model is valid")
} else {
	print("❌ Model has issues:")
	for issue in validation.errors {
		print("  ERROR: [\(issue.field)] \(issue.description)")
		if let suggestion = issue.suggestion {
			print("    Fix: \(suggestion)")
		}
	}
	for issue in validation.warnings {
		print("  WARNING: [\(issue.field)] \(issue.description)")
		if let suggestion = issue.suggestion {
			print("    Fix: \(suggestion)")
		}
	}
}

// Example issues:
//   WARNING: [revenueComponents] Model has expenses but no revenue
//     Fix: Add revenue components to calculate net income
//   ERROR: [Product Sales] NaN value in revenue 'Product Sales' for period 2025-Q4
//     Fix: Replace NaN with valid number or use fillMissing()
```

`validate(_:)` checks three things and only three: that the model is non-empty, that a
model with costs also has revenue, and that no revenue time series carries a `NaN`. It
does not check cycles between accounts; "Finding Dependency Cycles" below shows what you can
do about those.

### Finding Missing Data

Identify gaps in your model:

```swift
let missingDataDebugger = ModelDebugger(clock: docsClock, elapsedTime: docsElapsed)
let missing = await missingDataDebugger.findMissingData(in: model)

if missing.isEmpty {
    print("✅ No missing data")
} else {
    print("Missing Data:")
    for (account, periods) in missing {
        print("\(account):")
        for period in periods {
            print("  - \(period)")
        }
    }
}
```

### Finding Dependency Cycles

A ``FinancialModel``'s components hold time series, not formulas, so there is nothing in a
*built* model for a detector to walk — an account cannot refer to another account, and
therefore cannot refer to itself. Cycles live one layer up, where you decide what each
account's formula is, and that layer is ``ModelDefinition``.

``ModelDefinition/dependencyReport()`` reads the formulas — through
``FormulaEvaluator/accountNames(in:)``, which reports what a formula names **without
evaluating it** — and describes what it finds. It needs no data, so a set of definitions can
be checked when it is written rather than the first time it is run against a company:

```swift
// Gross profit is derived from revenue, and — by mistake — revenue has been derived
// back from gross profit.
let definitions = ModelDefinition<Double>()
    .defining("Revenue", as: "GrossProfit + COGS")
    .defining("GrossProfit", as: "Revenue - COGS")
    .defining("COGS", as: "Units * UnitCost")

let cycleReport = try definitions.dependencyReport()

if let evaluationOrder = cycleReport.evaluationOrder {
    print("✅ No dependency cycles. Order: \(evaluationOrder.joined(separator: ", "))")
} else {
    for cycle in cycleReport.cycles {
        print("⚠️  Cycle: \(cycle.path.joined(separator: " → "))")
        print("    Accounts: \(cycle.accounts.joined(separator: ", "))")
    }
}

print("Supply as data: \(cycleReport.requiredInputs.joined(separator: ", "))")

// Example output:
// ⚠️  Cycle: GrossProfit → Revenue → GrossProfit
//     Accounts: GrossProfit, Revenue
// Supply as data: UnitCost, Units
```

Names a formula reads that no formula defines — `Units` and `UnitCost` above — are leaves.
They are the data you supply, they have no dependencies of their own, and so they cannot take
part in a cycle. ``DependencyReport/requiredInputs`` is the list of them.

Three properties of that report are worth knowing before you rely on it:

- **Every cycle is reported, not the first one found.** The report is built from the graph's
  strongly connected components, so a model with three separate circularities names three. A
  walk that stopped at the first would have you fix one and re-run to be told about the next.
- **A cycle's identity is ``DependencyCycle/accounts``, not ``DependencyCycle/path``.**
  `A → B → C → A` and `B → C → A → B` are one cycle; which you are shown depends on where the
  walk entered, which depends on the names. Compare and record the account set. The path is
  for reading.
- **The report has no opinion.** It says a cycle is there, not that it is wrong — in a levered
  model a cycle is frequently deliberate. What it will not do is let one be evaluated:
  ``ModelDefinition/evaluate()`` and ``ModelDefinition/evaluationOrder()`` throw
  ``BusinessMathError/circularDependency(path:)`` rather than iterate a model nobody asked to
  have iterated. Asking for cycles to be resolved is a different call —
  ``ModelDefinition/solve(settings:)``, below.

One limitation to know up front, because it is the one most likely to matter. A formula reads
accounts **in the period being evaluated**, and the language has no reference to another
period — see <doc:1.9-FormulaEvaluation>. A roll-forward such as
`openingDebt(t) = closingDebt(t−1)` cannot be written, so the circular-interest models that
make cycles worth handling in a three-statement model cannot be built here yet. What is
supported is a cycle *within* a period, and that is what every example here is. Everything
below inherits that limit: the solver resolves a period, and carrying a closing balance into
the next one remains your loop.

### Can This Cycle Be Solved Exactly?

Each cycle carries a ``DependencyCycle/form``, read from the parse tree before any figures
exist. The formula grammar is `+ − × ÷` and nothing else, so this is decided rather than
estimated: a cycle is ``DependencyCycle/Form/linear`` when no member multiplies or divides
another member, and no member appears in a divisor.

An account a member's formula names but that sits *outside* the cycle is a coefficient, however
it is combined. `interest = debt * rate` is linear in `debt` when `rate` is supplied data — and
that is exact rather than a convenience, because nothing outside a strongly connected component
can depend on anything inside it, or it would be in the component.

```swift
let leveredDefinitions = ModelDefinition<Double>()
    .defining("interest", as: "debt * rate")
    .defining("debt", as: "openingDebt - cashFlow")
    .defining("cashFlow", as: "ebitda - interest")

for leveredCycle in try leveredDefinitions.dependencyReport().cycles {
    switch leveredCycle.form {
    case .linear:
        print("\(leveredCycle.accounts.joined(separator: ", ")): one exact answer")
    case .nonlinear:
        print("\(leveredCycle.accounts.joined(separator: ", ")): has to be iterated")
    }
}

// Example output:
// cashFlow, debt, interest: one exact answer
```

``DependencyReport/isExactlySolvable`` asks the same question of the whole model: `true` when it
is acyclic, and when every cycle in it is linear. It is a claim about the structure of the
formulas and not about the data — a linear system can still turn out to be singular once its
coefficients are known.

### Resolving a Cycle

``ModelDefinition/solve(settings:)`` evaluates the whole model and resolves its cycles instead
of refusing them. Calling it is the statement of intent ``ModelDefinition/evaluate()`` has no
way to infer.

A **linear** cycle is solved exactly. The coefficients are collected symbolically from the parse
tree, one *n*×*n* system is built per period, and Gaussian elimination gives the answer — no
tolerance, no iteration cap, no question of convergence. Gross-ups, cash sweeps and
profit-share accruals are all this shape:

```swift
let grossUpBase = TimeSeries(periods: [Period.month(year: 2026, month: 1)], values: [1_000.0])

let grossUp = ModelDefinition<Double>(inputs: ["base": grossUpBase])
    .defining("fee", as: "total * 0.10")
    .defining("total", as: "base + fee")

let grossedUp = try grossUp.solve()
print(grossedUp["total"]?.first ?? 0)
// 1111.111... — 1000 / 0.9, exactly
```

Two things a linear cycle can still fail to give you, both ``CycleSolverError``:

- ``CycleSolverError/underdetermined(accounts:period:detail:)`` — the formulas round the loop
  repeat one another, so more than one set of values satisfies all of them at once. `a = b + fee`
  together with `b = a - fee` is true of every pair a `fee` apart. Excel would iterate that and
  settle wherever it started.
- ``CycleSolverError/illConditioned(accounts:period:detail:)`` — the gain round the loop is
  within a rounding error of exactly 1, so every digit of the answer would come from
  cancellation.

A **nonlinear** cycle is iterated: Gauss–Seidel, sweeping the members in sorted name order, from
a starting iterate you name. ``IterationSettings`` governs that and nothing else — a linear
cycle reads none of it.

```swift
let unitSeries = TimeSeries(periods: [Period.month(year: 2026, month: 1)], values: [1.0])

let feedback = ModelDefinition<Double>(inputs: ["one": unitSeries])
    .defining("share", as: "one - share * share")

let settled = try feedback.solve(settings: IterationSettings(relaxation: 0.5))
```

If it does not settle, that **throws**. It does not come back as numbers with a flag on them,
because an unconverged iterate is in the right units, prints, and looks exactly like an answer:

```swift
do {
    _ = try feedback.solve()
} catch let solverError as CycleSolverError {
    if case .notConverged(let names, let state, let sweeps, let change, let moving) = solverError {
        print("\(names.joined(separator: ", ")) after \(sweeps) sweeps: \(state)")
        print("largest change \(change); still moving: \(moving.joined(separator: ", "))")
    }
    print(solverError.recoverySuggestion ?? "")
}
```

``ConvergenceState`` separates three things that need three different responses.
``ConvergenceState/oscillating`` is what a ``IterationSettings/relaxation`` below 1 exists for —
the iterate is stepping past the answer and back again. ``ConvergenceState/diverging`` is not
fixable by any setting: the loop amplifies, and the model has to change.
``ConvergenceState/exhausted`` is the one where raising ``IterationSettings/maxIterations`` is
worth trying, and the final change reported alongside is what tells you whether it was close.

## ModelProfiler: Performance Analysis

### Basic Performance Profiling

Measure execution time of operations:

```swift
import BusinessMath

let profiler = ModelProfiler(clock: docsClock, elapsedTime: docsElapsed)

// Measure a calculation
let cashFlows = [-5_000_000.0, -3_000_000, -2_000_000, 40_000_000]
let npvResult = await profiler.measure(operation: "NPV Calculation") {
	// The 2 ms this example reports is stated here rather than measured, so the report
	// below is the same on every machine. Drop this line and you measure the real call.
	docsElapsed.advance(by: .milliseconds(2))
	return npv(discountRate: 0.10, cashFlows: cashFlows)
}

// Get performance report
let report = await profiler.report()
print(report.formatted())
```

**Expected output:**
```
=== Performance Report ===
Generated: 2026-01-01 00:00:00 +0000
Total Operations: 1
Total Time: 0.00s

Operation                                Count    Total        Avg          Min          Max
-------------------------------------------------------------------------------------------------
NPV Calculation                          1        0.00         0.00         0.00         0.00
```

> Note: the columns show `0.00` because ``PerformanceReport/formatted()`` renders seconds to
> two decimal places, and 2 ms rounds to zero there. The precise value is on the statistics —
> `report.operations[0].averageTime` is `0.002`. If you need the finer figure, read it off
> ``OperationStatistics`` rather than off the formatted table.

### Profiling Multiple Operations

Track performance across many calculations:

```swift
// A named async function rather than `Task { … }`: an unstructured task is not awaited by
// anything, so a script that ends before it finishes prints nothing at all — and prints a
// *different* amount each time it is run. Everything below is awaited in order.
func profileMultipleOperations() async {
	let multiProfiler = ModelProfiler(clock: docsClock, elapsedTime: docsElapsed)

	let multiCompany = Entity(id: "ACME", primaryType: .ticker, name: "Acme Corp")
	let multiQ1 = Period.quarter(year: 2025, quarter: 1)
	let multiPeriods = [multiQ1, multiQ1 + 1, multiQ1 + 2, multiQ1 + 3]

	// Define financial data
	let revenueValues = [100_000.0, 110_000.0, 120_000.0, 130_000.0]
	let cogsValues = [60_000.0, 66_000.0, 72_000.0, 78_000.0]

	// Profile model building
	for _ in 1...100 {
		let multiModel = await multiProfiler.measure(operation: "Build Model") {
			// `advance(by:)` is what makes the durations below the same on every machine.
			// Drop these calls and the profiler measures the real work instead.
			docsElapsed.advance(by: .milliseconds(4))
			return buildModel(for: multiCompany) {
				Revenue("Sales", periods: multiPeriods, values: revenueValues)
				Expense("COGS", periods: multiPeriods, values: cogsValues, type: .costOfGoodsSold)
				FixedCost("OpEx", periods: multiPeriods, value: 20_000)
			}
		}

		// Profile calculations
		for period in multiPeriods {
			_ = await multiProfiler.measure(operation: "Calculate Net Income") {
				docsElapsed.advance(by: .microseconds(100))
				let revenue = multiModel.totalRevenue(for: period)
				let expenses = multiModel.totalExpenses(for: period)
				return revenue - expenses
			}
		}

		// Profile aggregations
		_ = await multiProfiler.measure(operation: "Annual Totals") {
			docsElapsed.advance(by: .microseconds(100))
			return multiPeriods.map { multiModel.totalRevenue(for: $0) }.reduce(0, +)
		}
	}

	// Get comprehensive report
	let multiReport = await multiProfiler.report(sortBy: .totalTime)
	print(multiReport.formatted())
}

await profileMultipleOperations()
```

**Expected output:**
```

Total Operations: 600
Total Time: 0.45s

Operation                                Count    Total        Avg          Min          Max
-------------------------------------------------------------------------------------------------
Build Model                              100      0.40         0.00         0.00         0.00
Calculate Net Income                     400      0.04         0.00         0.00         0.00

```


### Detecting Performance Bottlenecks

Identify slow operations automatically:

```swift
func detectBottlenecks() async {
	let bottleneckProfiler = ModelProfiler(clock: docsClock, elapsedTime: docsElapsed)

	await bottleneckProfiler.setWarningThreshold(0.001)

	let bottleneckCompany = Entity(id: "ACME", primaryType: .ticker, name: "Acme Corp")
	let bottleneckQ1 = Period.quarter(year: 2025, quarter: 1)
	let bottleneckPeriods = [bottleneckQ1, bottleneckQ1 + 1, bottleneckQ1 + 2, bottleneckQ1 + 3]

	// Define financial data
	let revenueValues = [100_000.0, 110_000.0, 120_000.0, 130_000.0]
	let cogsValues = [60_000.0, 66_000.0, 72_000.0, 78_000.0]

	// Profile model building. Each build is given 4 ms, comfortably over the 1 ms
	// threshold set above, so the example reliably demonstrates a detected bottleneck
	// rather than depending on how fast the machine happens to be.
	for _ in 0..<100 {
		await bottleneckProfiler.measure(operation: "Build Model") {
			docsElapsed.advance(by: .milliseconds(4))
			return buildModel(for: bottleneckCompany) {
				Revenue("Sales", periods: bottleneckPeriods, values: revenueValues)
				Expense("COGS", periods: bottleneckPeriods, values: cogsValues, type: .costOfGoodsSold)
				FixedCost("OpEx", periods: bottleneckPeriods, value: 20_000)
			}
		}
	}

	// Get bottlenecks
	let bottlenecks = await bottleneckProfiler.bottlenecks()

	if bottlenecks.isEmpty {
		print("✅ No performance issues")
	} else {
		print("⚠️  Performance Bottlenecks:")
		for op in bottlenecks {
			print("\(op.operation):")
			print("  Average Time: \(op.averageTime.number())s")
			print("  Executions: \(op.executionCount)")
			print("  Total Time: \(op.totalTime.number())s")
		}
	}

	// Verify performance with report
	let bottleneckReport = await bottleneckProfiler.report(sortBy: .totalTime)
	print(bottleneckReport.formatted())
}

await detectBottlenecks()
```

**Expected output:**
```
⚠️  Performance Bottlenecks:
Build Model:
  Average Time: 0.00s
  Executions: 100
  Total Time: 0.40s
=== Performance Report ===
Generated: 2026-01-01 00:00:00 +0000
Total Operations: 100
Total Time: 0.40s

-------------------------------------------------------------------------------------------------
```

The threshold is 1 ms and each build is given 4 ms, so `bottlenecks()` returns the

### Statistical Performance Analysis

Analyze performance distributions:

```swift
func analyzePerformanceDistribution() async {
	let statsProfiler = ModelProfiler(clock: docsClock, elapsedTime: docsElapsed)

	await statsProfiler.setWarningThreshold(0.001)

	let statsCompany = Entity(id: "ACME", primaryType: .ticker, name: "Acme Corp")
	let statsQ1 = Period.quarter(year: 2025, quarter: 1)
	let statsPeriods = [statsQ1, statsQ1 + 1, statsQ1 + 2, statsQ1 + 3]

	// Define financial data
	let revenueValues = [100_000.0, 110_000.0, 120_000.0, 130_000.0]
	let cogsValues = [60_000.0, 66_000.0, 72_000.0, 78_000.0]

	// Profile model building. Every tenth build is given 25 ms instead of 3 ms — a
	// deliberate skew, so the percentile and outlier arithmetic below has something real
	// to describe. A run where every execution takes the same time has no distribution
	// to analyse, and on a quiet machine that is very nearly what you measure.
	for iteration in 0..<100 {
		await statsProfiler.measure(operation: "Build Model") {
			docsElapsed.advance(by: iteration % 10 == 0 ? .milliseconds(25) : .milliseconds(3))
			return buildModel(for: statsCompany) {
				Revenue("Sales", periods: statsPeriods, values: revenueValues)
				Expense("COGS", periods: statsPeriods, values: cogsValues, type: .costOfGoodsSold)
				FixedCost("OpEx", periods: statsPeriods, value: 20_000)
			}
		}
	}

	// Get bottlenecks
	let statsBottlenecks = await statsProfiler.bottlenecks()

	if statsBottlenecks.isEmpty {
		print("✅ No performance issues")
	} else {
		print("⚠️  Performance Bottlenecks:")
		for op in statsBottlenecks {
			print("\(op.operation):")
			print("  Average Time: \(op.averageTime.number())s")
			print("  Executions: \(op.executionCount)")
			print("  Total Time: \(op.totalTime.number())s")
		}
	}

	// Verify performance with report
	let statsReport = await statsProfiler.report(sortBy: .totalTime)
	print(statsReport.formatted())

	let stats = statsReport.operations[0]

	print("Performance Statistics:")
	print("Executions: \(stats.executionCount)")
	print("Average: \(stats.averageTime.number())s")
	print("Std Dev: \(stats.stdDevTime.number())s")
	print("Min: \(stats.minTime.number())s")
	print("Max: \(stats.maxTime.number())s")
	print("Median: \(stats.medianTime.number())s")
	print("95th percentile: \(stats.percentile95.number())s")
	print("99th percentile: \(stats.percentile99.number())s")

	// Identify outliers
	if stats.maxTime > stats.averageTime * 3 {
		print("⚠️  Outliers detected - investigate max time operations")
	}
}

await analyzePerformanceDistribution()
```

```

  Average Time: 0.01s
  Executions: 100
  Total Time: 0.52s
=== Performance Report ===
Generated: 2026-01-01 00:00:00 +0000
Total Operations: 100
Total Time: 0.52s

Operation                                Count    Total        Avg          Min          Max
-------------------------------------------------------------------------------------------------
Build Model                              100      0.52         0.01         0.00         0.03
```

90 executions of 3 ms and 10 of 25 ms total 0.52s, so the mean is 5.2 ms and the maximum is
25 ms — comfortably past the `max > average × 3` test, which is why the outlier warning
fires. That is the shape you are looking for in a real profile: a median near the floor and
a 95th percentile several times higher says a minority of executions is carrying the cost,
and averaging alone would have hidden it.

```swift
func profileMemory() async {

	await memoryUsageProfiler.setWarningThreshold(0.001)

	// Profile model building
	for _ in 0..<100 {
		await memoryUsageProfiler.measure(operation: "Build Model") {

	// Read the statistics off *this* profiler's report. The example used to read

	// memory figures of an operation it never profiled.
```

```
Memory Usage:
Total Memory: 0 MB
Average per Execution: 0 MB
```

Zero is the honest answer here, not a placeholder: a four-account model built a hundred
times does not move the resident-set figure by a whole megabyte, and the report divides by
`1024 * 1024`. Read `stats.totalMemory` directly for the byte count.

## Logger: Category-Based Logging

### Setting Up Logging

BusinessMath extends `os.Logger` with pre-configured category loggers. Import `OSLog` alongside BusinessMath to use them:

```swift
import BusinessMath
import OSLog

// Get shared logger instance
let logger = Logger.shared

// Category-specific loggers are also available
let calculationLogger = Logger.calculations

// Log a message
let loggedAccountName = "Product Sales"
let loggedError: any Error = BusinessMathError.divisionByZero(context: "gross margin")

logger.info("Starting financial model calculation")
calculationLogger.debug("Processing period: \(q1.label)")
logger.warning("Missing data for account: \(loggedAccountName)")
logger.error("Calculation failed: \(loggedError)")
```

### Log Levels

Choose appropriate log levels:

```swift
let accountValue = 125_000.0
let irrError: any Error = BusinessMathError.calculationFailed(
    operation: "IRR",
    reason: "Cash flows must contain both positive and negative values"
)
let validationErrorCount = 3

// DEBUG: Detailed diagnostic information
logger.debug("Account value: \(accountValue), Period: \(q1.label)")

// INFO: General informational messages
logger.info("Model validation completed successfully")

// WARNING: Potentially problematic situations
logger.warning("Low data quality detected in time series")

// ERROR: Error events that might still allow continued operation
logger.error("Failed to calculate IRR: \(irrError.localizedDescription)")

// CRITICAL: Severe errors requiring immediate attention
logger.critical("Model validation failed with \(validationErrorCount) errors")
```

### Structured Logging

Log calculation lifecycle events with structured context:

```swift
let projectCashFlows = [-100_000.0, 30_000, 40_000, 50_000, 60_000]

logger.calculationStarted("NPV", context: [
    "discountRate": "0.10",
    "cashFlowCount": "\(projectCashFlows.count)"
])

let npvValue = npv(discountRate: 0.10, cashFlows: projectCashFlows)

logger.calculationCompleted("NPV", result: npvValue, duration: 0.003)

// Output:
// ▶️ Starting calculation: NPV
//    Context: discountRate=0.10, cashFlowCount=5
// ✅ Completed NPV in 0.003s
//    Result: 38877.13
```

### Performance Logging

Log performance metrics:

```swift
let start = Date()
```

## Common Issues and Diagnosis

### Issue: Unexpected Calculation Results

**Symptoms:**
- NPV or IRR values don't match expectations
- Revenue totals are incorrect
- Time series calculations produce NaN

**Diagnosis:**

```swift
let resultsDebugger = ModelDebugger(clock: docsClock, elapsedTime: docsElapsed)

// 1. Inspect input data
let resultsSnapshot = await resultsDebugger.snapshot(of: model)
for account in resultsSnapshot.accounts {
    // `values` is a dictionary, and Swift randomises its hash seed per process — printing
    // one directly gives a different key order on every run. Sort by period so the same
    // model always reads the same way, here and in your own diagnostics.
    let byPeriod = account.values.sorted { $0.key < $1.key }
    print("\(account.name): \(byPeriod.map { "\($0.key.label): \($0.value)" }.joined(separator: ", "))")
    // Check for NaN, negative values, or zeros
}

// 2. Trace calculation
await resultsDebugger.enableTracing()
let suspectCashFlows = [-100_000.0, 30_000, 40_000, 50_000, 60_000]
let result = try calculateNPV(discountRate: 0.10, cashFlows: suspectCashFlows)
let resultsTrace = await resultsDebugger.getTrace()
print(resultsTrace.formatted())

// 3. Validate model
let resultsValidation = await resultsDebugger.validate(model)
print(resultsValidation.detailedReport)
```

**Common Causes:**
- Missing or NaN values in time series
- Incorrect period alignment
- Wrong discount rate or parameters
- Formula errors in calculations

### Issue: Performance Degradation

**Symptoms:**
- Slow model building
- Long calculation times
- UI freezes during operations

**Diagnosis:**

```swift
let degradationProfiler = ModelProfiler(clock: docsClock, elapsedTime: docsElapsed)

// 1. Profile operations
_ = await degradationProfiler.measure(operation: "Build Model") {
    buildModel(for: company) {
        Revenue("Sales", periods: periods, values: [100_000, 110_000, 120_000, 130_000])
    }
}

// 2. Identify bottlenecks
let bottlenecks = await degradationProfiler.bottlenecks(threshold: 0.05)  // 50ms threshold
for op in bottlenecks {
    print("\(op.operation): \(op.averageTime)s")
}

// 3. Analyze distribution
let degradationReport = await degradationProfiler.report()
for op in degradationReport.operations {
    if op.maxTime > op.averageTime * 5 {
        print("⚠️  \(op.operation) has outliers")
    }
}
```

**Common Causes:**
- Too many accounts in model
- Inefficient loops or recursion
- Unnecessary recalculations
- Large time series operations

**Solutions:**
- Cache calculated values
- Use batch operations
- Optimize data structures
- Parallelize independent calculations

### Issue: Missing Data

**Symptoms:**
- NaN in results
- Incomplete time series
- Validation errors

**Diagnosis:**

```swift
let dataQualityDebugger = ModelDebugger(clock: docsClock, elapsedTime: docsElapsed)

// Find all missing data
let dataGaps = await dataQualityDebugger.findMissingData(in: model)

for (account, periods) in dataGaps {
    print("\(account) missing data:")
    for period in periods {
        print("  - \(period)")
    }
}

// Check data quality
let dataQualityValidation = await dataQualityDebugger.validate(model)
let dataIssues = dataQualityValidation.errors.filter { $0.rule == "no-nan-values" }

for issue in dataIssues {
    print(issue.description)
    print("Fix: \(issue.suggestion ?? "No suggestion")")
}
```

**Solutions:**
- Use `fillMissing()` to interpolate: `timeSeries.fillMissing()`
- Use `fillForward()`: `timeSeries.fillForward()`
- Add default values in model
- Fix data source

### Issue: Circular Dependencies

**Symptoms:**
- Stack overflow
- Infinite recursion
- Your own formula-resolution code never terminates

**Diagnosis:**

Inspect the definitions, not the built model — put them in a ``ModelDefinition`` and ask
``ModelDefinition/dependencyReport()``, which needs no data:

```swift
let suspectDefinitions = ModelDefinition<Double>()
    .defining("Revenue", as: "Margin * Cost")
    .defining("Cost", as: "Revenue * 0.6")

let suspectReport = try suspectDefinitions.dependencyReport()

for suspect in suspectReport.cycles {
    print(suspect.path.joined(separator: " → "))
    // "Cost → Revenue → Cost"
    print(suspect.form == .linear ? "linear — has an exact answer" : "nonlinear — needs iterating")

    let cycleError = BusinessMathError.circularDependency(path: suspect.path)
    print(cycleError.recoverySuggestion ?? "")
}
```

**Solutions:**
- If the cycle is a mistake, reorder so each account reads only values already computed, or
  break it with an intermediate value
- If the cycle is deliberate, call ``ModelDefinition/solve(settings:)`` rather than
  ``ModelDefinition/evaluate()`` — see "Resolving a Cycle" above
- Cross-period feedback, where the account that closes the loop should read the prior period's
  value, is not expressible yet: the formula language has no reference to another period

### Issue: Memory Leaks

**Symptoms:**
- Growing memory usage
- App crashes
- Slow performance over time

**Diagnosis:**

```swift
let memoryProfiler = ModelProfiler(clock: docsClock, elapsedTime: docsElapsed)

// Monitor memory over time
for iteration in 1...100 {
    _ = await memoryProfiler.measure(operation: "Iteration \(iteration)") {
        buildModel(for: company) {
            Revenue("Sales", periods: periods, values: [100_000, 110_000, 120_000, 130_000])
        }
    }

    if iteration % 10 == 0 {
        let report = await memoryProfiler.report(operations: ["Iteration \(iteration)"])
        let memory = report.operations[0].averageMemory
        print("Iteration \(iteration): \(memory / 1024 / 1024) MB")
    }
}

// If memory grows linearly, investigate for leaks
```

> Note: this is the one figure in the guide that is read from the machine rather than
> supplied. ``ModelProfiler`` takes an injectable clock and an injectable elapsed-time
> source, but its memory sampling has no equivalent — so a memory profile is a measurement
> of the process you actually ran. For a four-account model it reports `0 MB` on every
> iteration, which is why the output above is stable; a larger model, or a machine under
> pressure, will print something else. Read the trend, not the number.

**Solutions:**
- Clear caches periodically
- Use weak references where appropriate
- Release large objects when done
- Use Instruments Memory Profiler for detailed analysis

## Best Practices

### 1. Enable Debugging During Development

Always use debugging tools during development:

```swift
#if DEBUG
let developmentDebugger = ModelDebugger(clock: docsClock, elapsedTime: docsElapsed)
let developmentValidation = await developmentDebugger.validate(model)

if !developmentValidation.isValid {
    print("⚠️  Model validation failed:")
    print(developmentValidation.detailedReport)
}
#endif
```

### 2. Profile Performance Early

Profile performance before problems occur:

```swift
import Testing

let testProfiler = ModelProfiler(clock: docsClock, elapsedTime: docsElapsed)

// Profile in test suite
@Test("Model building performance")
func testModelPerformance() async {
    let result = await testProfiler.measure(operation: "Build Large Model") {
        buildModel(for: company) {
            Revenue("Sales", periods: periods, values: [100_000, 110_000, 120_000, 130_000])
        }
    }

    let report = await testProfiler.report()
    #expect(report.operations[0].averageTime < 0.1)  // Should be under 100ms
}
```

### 3. Use Appropriate Log Levels

`os.Logger` has no runtime level switch — the system decides which levels are
captured and persisted. Choose the level at the call site instead, and gate
verbose diagnostics on the build configuration:

```swift
#if DEBUG
// Development: emit the full diagnostic trail
logger.debug("Building model for \(company.name)")
#endif

// Any build: notice and above are persisted by the system,
// so reserve them for events worth keeping in production logs
logger.notice("Model built successfully")
```

### 4. Validate Models Before Production

Always validate before using in production:

```swift
func deployModel(_ model: FinancialModel) async throws {
    let debugger = ModelDebugger()
    let validation = await debugger.validate(model)

    guard validation.isValid else {
        throw BusinessMathError.validationFailed(errors: validation.errors.map(\.message))
    }

    // Proceed with deployment
}
```

### 5. Monitor Performance in Production

Track performance metrics:

```swift
let productionProfiler = ModelProfiler(clock: docsClock, elapsedTime: docsElapsed)

// In production, sample a percentage of requests
if Double.random(in: 0...1) < 0.01 {  // 1% sampling
    _ = await productionProfiler.measure(operation: "Production Calculation") {
        npv(discountRate: 0.10, cashFlows: cashFlows)
    }

    // Log if slow
    let report = await productionProfiler.report()
    if let op = report.operations.first, op.averageTime > 0.5 {
        logger.warning("Slow calculation detected: \(op.averageTime)s")
    }
}
```
