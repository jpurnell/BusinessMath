# Formula Evaluation

Define derived accounts as configuration rather than code.

## Overview

Two companies rarely build their statements the same way. One reports fulfilment inside cost of
sales, another below it. One carries eleven revenue lines where another carries one. Neither is
wrong — they are describing different businesses, and their accountants made different calls.

That is fine until you want to compare them. Gross margin is a simple idea, but the arithmetic
that produces it differs per company, and hard-coding one version means every new company is a
code change.

``FormulaEvaluator`` lets the arithmetic be data. Start with two accounts over a quarter:

```swift
let jan = Period.month(year: 2026, month: 1)
let feb = Period.month(year: 2026, month: 2)
let mar = Period.month(year: 2026, month: 3)

let revenue      = TimeSeries(periods: [jan, feb, mar], values: [100.0, 200.0, 300.0])
let costOfSales  = TimeSeries(periods: [jan, feb, mar], values: [40.0, 80.0, 120.0])
```

```swift
let evaluator = FormulaEvaluator(accounts: [
    "revenue": revenue,
    "cogs": costOfSales
])

let grossProfit = try evaluator.evaluate("revenue - cogs")
let grossMargin = try evaluator.evaluate("(revenue - cogs) / revenue")
```

A formula is an arithmetic expression over named accounts. It returns a ``TimeSeries``, so the
result is an account like any other and can be charted, aggregated or fed to a ratio.

## Names as they actually appear

A chart of accounts is not a set of identifiers. Real names carry spaces, ampersands and
slashes, so a name can be bracketed and is then taken literally:

```swift
// The same two accounts, under the names a ledger would actually carry.
let ledger = FormulaEvaluator(accounts: [
    "Total Revenue":      revenue,
    "Cost of Goods Sold": costOfSales,
    "Sales & Marketing":  TimeSeries(periods: [jan, feb, mar], values: [10.0, 20.0, 30.0]),
    "cogs":               costOfSales
])

let operatingProfit = try ledger.evaluate(
    "[Total Revenue] - [Cost of Goods Sold] - [Sales & Marketing]")
print(operatingProfit.valuesArray)   // [50.0, 100.0, 150.0]
```

Without brackets, `Cost of Goods Sold` reads as three separate accounts and `A/P` as a
division. Bare identifiers still work where the name allows it, and the two mix freely:

```swift
let mixed = try ledger.evaluate("[Total Revenue] - cogs")
print(mixed.valuesArray)   // [60.0, 120.0, 180.0]
```

## One analysis, two companies

This is what the type is for. The company definitions differ; the analysis does not.

```swift
let northwind = [
    "Revenue":      "[Product Revenue] + [Service Revenue]",
    "Gross Profit": "[Product Revenue] + [Service Revenue] - [Cost of Goods Sold] - [Fulfilment]",
    "Opex":         "[Sales & Marketing] + [R&D]"
]

let contoso = [
    "Revenue":      "[Total Revenue]",
    "Gross Profit": "[Total Revenue] - [Cost of Sales]",
    "Opex":         "[Selling Expense] + [Engineering]"
]
```

Northwind splits revenue in two and reports fulfilment separately; Contoso folds fulfilment into
cost of sales and reports one revenue line. Evaluate each definition against its own accounts
and both produce a `Revenue`, a `Gross Profit` and an `Opex` that mean the same thing.

Derived accounts can then feed further formulas, because the output of one evaluation is input
to the next:

```swift
// Contoso's own accounts, named the way Contoso names them.
let contosoAccounts = [
    "Total Revenue":   revenue,
    "Cost of Sales":   costOfSales,
    "Selling Expense": TimeSeries(periods: [jan, feb, mar], values: [10.0, 20.0, 30.0]),
    "Engineering":     TimeSeries(periods: [jan, feb, mar], values: [15.0, 15.0, 15.0])
]

var derived: [String: TimeSeries<Double>] = [:]
for (label, formula) in contoso {
    derived[label] = try FormulaEvaluator(accounts: contosoAccounts).evaluate(formula)
}

let second = FormulaEvaluator(accounts: derived)
let margin = try second.evaluate("[Gross Profit] / Revenue * 100")
let ebitda = try second.evaluate("[Gross Profit] - Opex")
```

## What happens when periods do not line up

Every operation is the corresponding ``TimeSeries`` operator, so a formula and the same
expression written in Swift give the same answer. Those operators intersect: a period survives
only where both sides have a value.

That matters more than it sounds. Suppose February's cost line is missing:

```swift
// The same revenue, but February's cost line never arrived.
let gappyCosts = TimeSeries(periods: [jan, mar], values: [40.0, 120.0])
let gappy = FormulaEvaluator(accounts: ["revenue": revenue, "cogs": gappyCosts])

let gappyGrossProfit = try gappy.evaluate("revenue - cogs")
// periods: [jan, mar] — February is absent, not zero
```

If a missing cost were read as zero, February would report £200 of gross profit on £200 of
revenue: a plausible number, in the right units, sitting in the right column, and wrong by the
whole of the cost line. Dropping the period says "we do not know", which is the truth and is
visible.

Division is the one place the operator's behaviour shows through: a zero denominator produces a
non-finite value rather than throwing, exactly as `/` does on two series. Check `isFinite` where
a denominator can reach zero.

## Validating a definition before any data is loaded

A configuration can be checked for the accounts it requires without those accounts existing:

```swift
let required = try FormulaEvaluator<Double>.accountNames(
    in: "([Total Revenue] - cogs) / [Total Revenue]")
// ["Total Revenue", "cogs"]
```

Useful when onboarding a company: read every formula in its definition, collect the names, and
report which are missing from the incoming data before running anything.

## Refusals

An account the formula names but nobody supplied is refused rather than defaulted:

```swift
do {
    let operatingProfit = try evaluator.evaluate("revenue - opex")
    print(operatingProfit.valuesArray)
} catch FormulaError.unknownAccount(let name) {
    print("no account named \(name)")   // no account named opex
}
```

Defaulting to zero would make that expression return revenue and present it as a profit figure.
The other refusals are ``FormulaError/invalidSyntax(_:)``,
``FormulaError/unbalancedParentheses``, ``FormulaError/unterminatedAccountName``,
``FormulaError/unexpectedEnd`` and ``FormulaError/unexpectedCharacter(_:)``.

## Functions

A formula may call a function, and every one acts **period by period** — what a spreadsheet
formula does when it is filled across a row.

```swift
let quarters = [
    Period.quarter(year: 2026, quarter: 1),
    Period.quarter(year: 2026, quarter: 2)
]

let sweep = ModelDefinition<Double>(
    inputs: [
        "available": TimeSeries(periods: quarters, values: [100, 40]),
        "outstanding": TimeSeries(periods: quarters, values: [60, 60])
    ]
)
.defining("paydown", as: "MIN(MAX(available, 0), outstanding)")
```

`IF` and the comparison operators make a conditional expressible, with `TRUE` and `FALSE`
behaving as 1 and 0 exactly as they do in a sheet.

```swift
let tax = ModelDefinition<Double>(
    inputs: [
        "profit": TimeSeries(periods: quarters, values: [50, -10]),
        "rate": TimeSeries(periods: quarters, values: [0.25, 0.25])
    ]
)
.defining("tax", as: "IF(profit > 0, profit * rate, 0)")
```

`NPV`, `IRR` and the statistical names aggregate instead: they consume a whole series and give
one number, constant across the periods it came from.

Names bind to the canonical implementation rather than to a second one written here, and where
Excel's definition differs from the textbook's, **the formula grammar means Excel's** — a
formula string came out of a sheet.

- `NPV` discounts every cash flow by at least one period. ``npv(discountRate:cashFlows:)``
  leaves the first undiscounted; the two differ by a period of compounding. Call it directly
  when the textbook form is wanted, where the choice is explicit.
- `PMT`, `IPMT` and `PPMT` are negative for money leaving, as Excel returns them, while
  ``payment(presentValue:rate:periods:futureValue:type:)`` returns the magnitude.
- `STDEV` divides by *n − 1* and `STDEVP` by *n*, as their Excel names promise.

A name the evaluator does not have is an error, never a zero:

```swift
let unknown = ModelDefinition<Double>(
    inputs: ["x": TimeSeries(periods: quarters, values: [1, 2])]
)
.defining("y", as: "VLOOKUP(x, x)")

do {
    _ = try unknown.evaluate()
} catch let error as FormulaError {
    // .unknownFunction("VLOOKUP") — never a substituted value
    print(error)
}
```

## Carrying a balance forward

A formula still cannot read another period, and that is deliberate: supporting it would mean
tracking dependencies per account *and* period rather than per account, which is a different
evaluator. The carry is explicit instead, as data.

``PeriodDriver`` runs the model once per period, seeding each opening account from the previous
period's closing value.

```swift
let years = [Period.year(2026), Period.year(2027), Period.year(2028)]

let debt = ModelDefinition<Double>(
    inputs: ["repayment": TimeSeries(periods: years, values: [10, 10, 10])]
)
.defining("closingDebt", as: "openingDebt - repayment")

let driver = PeriodDriver(
    definition: debt,
    rollforwards: [
        Rollforward(opening: "openingDebt", closing: "closingDebt", seed: 100.0)
    ]
)

let schedule = try driver.run(over: years)
// openingDebt: 100, 90, 80
// closingDebt:  90, 80, 70
```

The two kinds of circularity stay separate, and neither does the other's job:

| Circularity | Resolved by |
|---|---|
| Within one period — interest on an average balance | ``ModelDefinition/solve(settings:)`` |
| Across periods — a closing balance opens the next | ``PeriodDriver`` |

That separation is what lets interest depend on a repayment that depends on the interest,
converging inside a period, while the balance still moves forward between periods without
either mechanism seeing the other.

## What it deliberately does not do

No references to other periods, and no aggregation *inside* a period-wise formula. A formula
reads accounts in the period being evaluated; anything that looks across periods is either a
time series operation — see <doc:1.2-TimeSeries> for moving averages, growth rates and period
conversion — or a rollforward, which is data.

Keeping the language small remains deliberate. It is configuration written by whoever knows the
company's accounting, and every feature added to it is another way for that configuration to be
subtly wrong. Functions were added because a cash sweep is not expressible without `MIN`, and
each registered name carries a verified Excel meaning rather than a plausible one.
