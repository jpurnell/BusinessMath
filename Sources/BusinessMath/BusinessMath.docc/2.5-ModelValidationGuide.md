# Model Validation with Fake-Data Simulation

Check if your statistical models can recover parameters from simulated data.

## Overview

Before fitting a statistical model to real data, you should always verify that your fitting procedure works correctly. **Fake-data simulation** (also called simulation-based calibration or SBC) is a fundamental validation technique: simulate data from your model with known parameters, then check if your fitting procedure can recover those parameters.

This guide implements the workflow described by Andrew Gelman in his blog post "[Simulating from and checking a model in Stan](https://statmodeling.stat.columbia.edu/2025/12/15/simulating-from-and-checking-a-model-in-stan/)".

### What You'll Learn

- Why fake-data simulation is essential before using real data
- How to implement the parameter recovery workflow
- What problems this technique can catch
- How to interpret validation results

## The Fundamental Workflow

The fake-data simulation workflow has four steps:

1. **Specify true parameters** - Choose specific parameter values
2. **Simulate fake data** - Generate data from your model using those parameters
3. **Fit the model** - Apply your estimation procedure to the simulated data
4. **Check recovery** - Compare recovered parameters to true parameters

If your procedure **cannot** recover parameters from data you simulated yourself, something is wrong with your model, algorithm, or implementation.

```swift
// Step 1: Specify true parameters
let trueA = 0.2
let trueB = 0.3
let trueSigma = 0.2

// Steps 2-4: Run complete validation.
// `recoveryCheck` is defined under "Reproducibility" below: it is the shipped
// `ReciprocalParameterRecoveryCheck.run` plus a `seed:`, so this guide's figures
// are the figures you get.
let report = try recoveryCheck(
    trueA: trueA,
    trueB: trueB,
    trueSigma: trueSigma,
    n: 100,
    xRange: 0.0...10.0,
    seed: 8_675_309
)

print(report.summary)
// Shows whether each parameter was recovered within tolerance
```

The very first run in this guide fails — on `sigma`, by 12% against a 10% tolerance. That is
not an accident of the seed, and it is worth understanding before you read any further,
because it is the single most common way to misread a recovery check.

`a` and `b` came back to within about 1%. `sigma` did not, and it never reliably will at this
sample size: the maximum-likelihood estimator of a residual standard deviation has a relative
standard error of roughly `1 / sqrt(2n)`, which at `n = 100` is **7.1%**. A 10% tolerance is
1.41 standard errors out, so a correct, bug-free implementation fails this check about
**one run in six** — from sampling noise alone. The replicate summary below measures exactly
that (8 of 10 passed); the sample-size sweep shows it disappearing once `n` reaches 200.

So: a single ✗ on `sigma` at `n = 100` tells you almost nothing. What would tell you
something is a *systematic* miss — `a` and `b` off in the same direction across replicates,
or an error many standard errors wide. Fake-data simulation is only a useful check when you
know how wide its own noise is.

## Reproducibility

Fake-data simulation is only useful if you can rerun it. A validation report that changes
every time you run it cannot be quoted in a commit message, pinned in a test, or compared
against last week's.

The shipped ``ReciprocalRegressionSimulator`` and ``ReciprocalParameterRecoveryCheck`` draw
their fake data from the system generator: neither `simulate(n:xRange:)` nor `run(...)`
takes a `seed:` or a `RandomNumberGenerator`, so every call produces a different dataset and
a different report. That is convenient interactively and useless for a published figure.

Simulating through an explicit generator is a few lines, because ``DistributionNormal``
conforms to ``SeedableDistribution`` — it exposes `next(using:)`, which takes all of its
randomness from a generator you supply:

```swift
/// Simulate `n` observations from `y ~ Normal(1 / (a + b·x), sigma)`, drawing every
/// value from `generator`. Seed the generator and the fake data repeats exactly.
func simulateReciprocal<G: RandomNumberGenerator>(
    a: Double,
    b: Double,
    sigma: Double,
    n: Int,
    xRange: ClosedRange<Double>,
    using generator: inout G
) -> [ReciprocalRegressionModel<Double>.DataPoint] {
    let params = ReciprocalRegressionModel<Double>.Parameters(a: a, b: b, sigma: sigma)
    return (0..<n).map { _ in
        let x = Double.random(in: xRange, using: &generator)
        let mu = ReciprocalRegressionModel<Double>.predictedMean(x: x, params: params)
        let y = DistributionNormal(mu, sigma).next(using: &generator)
        return ReciprocalRegressionModel<Double>.DataPoint(x: x, y: y)
    }
}
```

The rest of the workflow is already deterministic — gradient descent on a fixed dataset
returns the same answer every time — so seeding the simulation is enough to pin the whole
report:

```swift
/// The four-step check, seeded: simulate, fit, compare, report.
func recoveryCheck(
    trueA: Double,
    trueB: Double,
    trueSigma: Double,
    n: Int = 100,
    xRange: ClosedRange<Double> = 0.0...10.0,
    tolerance: Double = 0.10,
    learningRate: Double = 0.001,
    maxIterations: Int = 1_000,
    seed: UInt64
) throws -> ParameterRecoveryReport<Double> {
    // Step 2: simulate fake data from the true parameters
    var generator = SplitMix64(seed: seed)
    let data = simulateReciprocal(
        a: trueA, b: trueB, sigma: trueSigma,
        n: n, xRange: xRange, using: &generator
    )

    // Step 3: fit
    let fit = try ReciprocalRegressionFitter<Double>().fit(
        data: data,
        initialGuess: ReciprocalRegressionModel<Double>.Parameters(a: 0.5, b: 0.5, sigma: 0.5),
        learningRate: learningRate,
        maxIterations: maxIterations
    )

    // Step 4: compare recovered against true
    let truth = ["a": trueA, "b": trueB, "sigma": trueSigma]
    let recovered = [
        "a": fit.parameters.a,
        "b": fit.parameters.b,
        "sigma": fit.parameters.sigma
    ]

    var absoluteErrors: [String: Double] = [:]
    var relativeErrors: [String: Double] = [:]
    var withinTolerance: [String: Bool] = [:]
    for (name, trueValue) in truth {
        let absError = abs(recovered[name]! - trueValue)
        let relError = absError / abs(trueValue)
        absoluteErrors[name] = absError
        relativeErrors[name] = relError
        withinTolerance[name] = relError <= tolerance
    }

    return ParameterRecoveryReport(
        trueParameters: truth,
        recoveredParameters: recovered,
        absoluteErrors: absoluteErrors,
        relativeErrors: relativeErrors,
        withinTolerance: withinTolerance,
        tolerance: tolerance,
        sampleSize: n,
        converged: fit.converged,
        iterations: fit.iterations,
        logLikelihood: fit.logLikelihood
    )
}
```

Every number printed in this guide comes from `recoveryCheck` with a stated seed. Use the
shipped `ReciprocalParameterRecoveryCheck.run` when you want a fresh draw each time; use a
seeded check when the result has to be comparable — which, for a validation run, is most of
the time.

## Why This Matters

### It's Not Obvious That Fitting Will Work

Even with correct model specification, fitting can fail for many reasons:

- **Poor identification**: Some parameter combinations produce identical data
- **Poor mixing**: Optimization gets stuck in local minima
- **Numerical instability**: Round-off errors accumulate
- **Coding bugs**: Implementation doesn't match mathematical specification
- **Algorithmic issues**: Optimizer can't handle the problem structure

### What This Check Tells You

**If you CAN'T recover parameters**:
- ❌ Your fitting procedure has fundamental problems
- Don't use it on real data until you fix the issues
- Investigate: Is it identification? Optimization? A bug?

**If you CAN recover parameters**:
- ✓ Your fitting procedure passes minimum sanity check
- ⚠️ This doesn't prove your model is appropriate for real data
- ⚠️ This doesn't guarantee you'll get good results on real data
- It just means your implementation works as intended

As Gelman notes: "It's a minimum check. If you're program *can't* fit data simulated from the model, then that's something that you'll want to know right away."

## The Reciprocal Regression Example

BusinessMath includes a complete implementation based on Gelman's Stan example: a nonlinear regression with reciprocal form.

### The Model

The model relates response `y` to predictor `x` through:

```
y[i] ~ Normal(μ[i], σ)
μ[i] = 1 / (a + b * x[i])
```

Where:
- `a` > 0: Intercept parameter
- `b` > 0: Slope parameter
- `σ` > 0: Residual standard deviation

This model appears in pharmacokinetics (Michaelis-Menten kinetics), economics (reciprocal demand curves), and other fields.

### Step-by-Step Implementation

#### 1. Simulate Data

Draw fake data from the true parameter values, through a seeded generator:

```swift
// Generate 100 observations with x uniform on [0, 10].
// `simulateReciprocal` is the seeded simulator from "Reproducibility" above;
// `ReciprocalRegressionSimulator(a:b:sigma:).simulate(n:xRange:)` is the shipped
// equivalent, minus the seed.
var dataGenerator = SplitMix64(seed: 8_675_309)
let data = simulateReciprocal(
    a: 0.2, b: 0.3, sigma: 0.2,
    n: 100, xRange: 0.0...10.0,
    using: &dataGenerator
)

// Each data point contains (x, y)
for point in data.prefix(5) {
    print("x = \(point.x), y = \(point.y)")
}
```

**Output:**
```
x = 0.1744188228363508, y = 3.9805818260987618
x = 4.259227293900345, y = 0.6686588005002471
x = 8.620465445948327, y = 0.3217936012563091
x = 3.803196221081567, y = 1.1149675288202863
x = 2.51039407530383, y = 1.0521080807930983
```

**How parameter recovery works:**

The x values (uniform on [0, 10]) are just the **locations** where we observe y. The parameters define the **relationship** between x and y:

```swift
// For each x, generate y according to:
// y = 1/(a + b*x) + noise, where noise ~ Normal(0, sigma)

// With a=0.2, b=0.3, this creates specific y patterns:
let x1 = 1.0
let mu1 = 1.0 / (0.2 + 0.3 * x1)  // = 1/0.5 = 2.0

let x5 = 5.0
let mu5 = 1.0 / (0.2 + 0.3 * x5)  // = 1/1.7 ≈ 0.588

let x10 = 10.0
let mu10 = 1.0 / (0.2 + 0.3 * x10)  // = 1/3.2 ≈ 0.313

// The pattern of y values across different x values encodes a, b, sigma!
// Maximum likelihood finds the a, b, sigma that best explain this pattern
```

Think of it like this:
- **x values**: Where you choose to take measurements (controllable)
- **True parameters**: The hidden mechanism generating y from x
- **Observed y values**: Noisy realizations that reveal the mechanism
- **Parameter recovery**: Reverse-engineering the mechanism from observations

#### 2. Fit the Model

Use maximum likelihood estimation to recover parameters:

```swift
let fitter = ReciprocalRegressionFitter<Double>()

let result = try fitter.fit(
    data: data,
    initialGuess: ReciprocalRegressionModel<Double>.Parameters(
        a: 0.5, b: 0.5, sigma: 0.5
    ),
    learningRate: 0.001,
    maxIterations: 1000
)

print("Fitted parameters:")
print("  a = \(result.parameters.a)")
print("  b = \(result.parameters.b)")
print("  sigma = \(result.parameters.sigma)")
print("  Converged: \(result.converged)")
```

**Output:**
```
Fitted parameters:
  a = 0.19837232476300654
  b = 0.2963690410054798
  sigma = 0.22407264351774328
  Converged: true
```

#### 3. Validate Recovery

Compare recovered parameters to true values:

```swift
let trueParams = ["a": 0.2, "b": 0.3, "sigma": 0.2]
let recoveredParams = [
    "a": result.parameters.a,
    "b": result.parameters.b,
    "sigma": result.parameters.sigma
]

// Sort at the print site. Swift randomises its hash seed per process, so iterating a
// dictionary directly prints these three lines in a different order on every run.
for (name, trueValue) in trueParams.sorted(by: { $0.key < $1.key }) {
    let recovered = recoveredParams[name]!
    let relError = abs(recovered - trueValue) / abs(trueValue)
    let status = relError <= 0.10 ? "✓ PASS" : "✗ FAIL"

    print("\(name): true = \(trueValue), recovered = \(recovered) \(status)")
}
```

**Output:**
```
a: true = 0.2, recovered = 0.19837232476300654 ✓ PASS
b: true = 0.3, recovered = 0.2963690410054798 ✓ PASS
sigma: true = 0.2, recovered = 0.22407264351774328 ✗ FAIL
```

Same dataset, same three verdicts as the summary at the top of the guide — `sigma` is 12%
high, which at `n = 100` is inside the estimator's own noise.

while `a` and `b` are still within 3% — gradient descent here often exhausts its budget
before its step size falls under tolerance, without that costing much accuracy. Raising
`maxIterations` to 20,000 does not measurably change any of these three estimates.

## Advanced Validation

### Multiple Replicates

Run the check multiple times to assess average performance:

```swift
// Ten independent datasets: one base seed, one replicate index. Derive the seeds rather
// than reusing one — replicates sharing a seed are the same dataset ten times over.
let reports = try (0..<10).map { replicate in
    try recoveryCheck(
        trueA: 0.2,
        trueB: 0.3,
        trueSigma: 0.2,
        n: 100,
        seed: 8_675_309 &+ UInt64(replicate)
    )
}

print(ReciprocalParameterRecoveryCheck.summarizeReplicates(reports))
// Shows pass rate and average errors across replicates
```

**Output:**
```
Parameter Recovery: Multiple Replicates Summary
===============================================

Replicates: 10
Passed: 8 (80.0%)
Failed: 2

Average Relative Errors:
------------------------
a: 3.19%
b: 3.76%
sigma: 4.75%
```

`ReciprocalParameterRecoveryCheck.runMultiple(...)` does the same thing without the seeds.

This is the number that puts the two individual failures above in proportion. Eight of ten
replicates pass; the average error on `sigma` is 4.75%, against the ~5.6% mean absolute error
you would predict from `1 / sqrt(2n)` alone. The procedure is behaving as a correct
maximum-likelihood fit should — the 10% tolerance is simply narrower than `sigma`'s sampling
distribution at `n = 100`, so roughly one replicate in six is expected to trip it.

A pass rate near 100% here would mean the tolerance was loose, not that the model was better.

This is closer to full simulation-based calibration (SBC), which Gelman describes as drawing parameters from the prior and checking coverage properties.

### Sample Size Effects

Investigate how much data you need for reliable recovery:

```swift
let sampleSizes = [20, 50, 100, 200, 500]

for n in sampleSizes {
    let report = try recoveryCheck(
        trueA: 0.2, trueB: 0.3, trueSigma: 0.2,
        n: n,
        seed: 5_551_212
    )

    let errors = report.relativeErrors.sorted { $0.key < $1.key }
        .map { "\($0.key) \($0.value.percent(1))" }
        .joined(separator: ", ")

    print("N = \(n): \(report.passed ? "✓" : "✗")  " +
          "converged: \(report.converged ? "yes" : "no"), " +
          "\(report.iterations) iterations — \(errors)")
}
```

**Output:**
```
N = 20: ✗  converged: no, 1000 iterations — a 91.3%, b 22.4%, sigma 38.7%
N = 50: ✗  converged: no, 1000 iterations — a 0.5%, b 2.9%, sigma 26.0%
N = 100: ✓  converged: no, 1000 iterations — a 0.0%, b 3.5%, sigma 8.2%
N = 200: ✓  converged: no, 1000 iterations — a 0.2%, b 3.0%, sigma 2.5%
N = 500: ✗  converged: yes, 147 iterations — a 381,324,500,753.6%, b 248,361,624.2%, sigma 574.8%
```

Read that last line before anything else. **At `N = 500` the fit does not merely miss — it
diverges by eleven orders of magnitude, and reports `converged: yes` while doing it.**

This is the failure the whole technique exists to catch, and it is a property of the fitter,
not of this seed: `ReciprocalRegressionFitter.fit` uses a fixed `learningRate` (default
`0.001`) against a negative log-likelihood that sums over all `n` observations, so the
gradient grows with sample size. Past roughly `n = 500` the step overshoots, the iterate runs
away, and the step-size convergence test then trips — because a diverged iterate stops
moving too. `converged: true` here means "stopped", not "found the optimum".

The practical consequences:

- Never read `converged` without also reading the parameters. A converged fit at an absurd
  parameter value is worse than an unconverged one at a sensible value.
- Scale the learning rate with sample size, or divide the objective by `n`, before fitting
  larger datasets. The same `N = 500` dataset at `learningRate: 0.0001` recovers
  `a = 0.2015, b = 0.2962, sigma = 0.1973` in 225 iterations — a clean pass. One order of
  magnitude on a single argument is the whole difference between the two outcomes.
- The trend from `N = 20` to `N = 200` is the one theory predicts — `sigma`'s error falls
  38.7% → 26.0% → 8.2% → 2.5%, roughly as `1 / sqrt(n)`. Recovery does improve with sample
  size. `N = 500` is not a counter-example to that; it is a bug sitting on top of it.

### Stress Testing

Try difficult scenarios to find where your procedure breaks:

```swift
// 1. High noise
let highNoise = try recoveryCheck(
    trueA: 0.2, trueB: 0.3, trueSigma: 1.0,  // Large sigma
    seed: 271_828
)
print("High noise:          \(highNoise.passed ? "✓ PASS" : "✗ FAIL")")

// 2. Extreme parameter values
let extremeParams = try recoveryCheck(
    trueA: 0.001, trueB: 10.0, trueSigma: 0.1,
    seed: 271_829
)
print("Extreme parameters:  \(extremeParams.passed ? "✓ PASS" : "✗ FAIL")")

// 3. Poor initialization
let poorInitFitter = ReciprocalRegressionFitter<Double>()
let poorInit = try poorInitFitter.fit(
    data: data,
    initialGuess: ReciprocalRegressionModel<Double>.Parameters(a: 10.0, b: 10.0, sigma: 5.0),  // Way off
    maxIterations: 100
)
print("Poor initialization: a = \(poorInit.parameters.a.number(3)), " +
      "b = \(poorInit.parameters.b.number(3)), " +
      "sigma = \(poorInit.parameters.sigma.number(3))")
```

**Output:**
```
High noise:          ✗ FAIL
Extreme parameters:  ✗ FAIL
Poor initialization: a = 8.773, b = 9.251, sigma = 1.333
```

All three do what a stress test is supposed to do — they break.

- **High noise** (`sigma = 1.0`, five times the signal at `x = 10`): with the same 100
  observations there is far less information about the curve, and 10% recovery is out of
  reach. Expected, and not a defect.
- **Extreme parameters** (`a = 0.001`, `b = 10.0`): `a` is four orders of magnitude below
  `b`, so over `x ∈ [0, 10]` the `a` term is invisible against `b·x` for all but the smallest
  `x`. This is a genuine identification problem, not an optimizer problem — no amount of data
  at these `x` values recovers `a` to 10%.
- **Poor initialization** (starting at `a = b = 10`, capped at 100 iterations) barely moves:
  `a` goes 10 → 8.77, `b` 10 → 9.25. The optimizer is not stuck in a local minimum, it has
  simply not been given enough steps to travel that far at `learningRate: 0.001`.

## Interpreting Results

### The Validation Report

The `ParameterRecoveryReport` contains:

- **True parameters**: Values used for simulation
- **Recovered parameters**: Values from fitting
- **Absolute errors**: |recovered - true|
- **Relative errors**: |recovered - true| / |true|
- **Within tolerance**: Boolean for each parameter
- **Convergence info**: Did optimization converge?
- **Overall status**: Did all parameters pass?

```swift
let reportSample = try recoveryCheck(trueA: 0.2, trueB: 0.3, trueSigma: 0.2, seed: 1_618_034)

if reportSample.passed {
	print("✓ Model validation passed!")
	print("  All parameters recovered within \(reportSample.tolerance.percent()) tolerance")
} else {
	print("✗ Model validation failed!")
	print("  Check which parameters failed:")
	// Sorted, so the failing parameters list in the same order every run
	for (name, passed) in reportSample.withinTolerance.sorted(by: { $0.key < $1.key }) {
		if !passed {
			print("  - \(name): \(reportSample.relativeErrors[name]!.percent()) error")
		}
	}
}
```

**Output:**
```
✓ Model validation passed!
  All parameters recovered within 10.00% tolerance
```

### Common Failure Modes

**Non-convergence**:
```
Converged: No
Iterations: 1000 (hit maximum)
```
→ Try: More iterations, better initialization, different learning rate.

→ But check first whether it matters. Across the ten replicates above, raising
`maxIterations` from 1,000 to 20,000 left the pass rate at 8/10, the average error on `sigma`
at 4.75%, and `converged` at 6 of 10 — nothing moved. The optimizer had already arrived;
only its step-size stopping test disagreed. Non-convergence that costs no accuracy is a
stopping-rule problem, not an estimation problem. Conversely — see the `N = 500` case above —
`converged: Yes` is no evidence at all that the fit is good.

**Large systematic bias**:
```
Parameter | True  | Recovered | Status
a         | 0.200 | 0.350     | ✗ FAIL
b         | 0.300 | 0.450     | ✗ FAIL
```
→ Possible identification problem or optimization getting stuck

**High variance**:
```
Replicate 1: a = 0.19 ✓
Replicate 2: a = 0.35 ✗
Replicate 3: a = 0.21 ✓
```
→ Unstable estimation, may need more data or better algorithm

## Best Practices

### 1. Always Validate Before Using Real Data

<!-- docs:illustrative -->
```swift
// DON'T:
let model = MyComplexModel()
let results = try model.fit(realWorldData)  // Hope it works!

// DO:
let validation = try MyComplexModel.validateOnFakeData()
if validation.passed {
    let results = try model.fit(realWorldData)
} else {
    print("Fix validation issues first!")
}
```

### 2. Use Realistic Parameter Values

Choose true parameters that reflect your actual application:

```swift
// If real data has small effects...
_ = try recoveryCheck(
    trueA: 0.01, trueB: 0.02, trueSigma: 0.001,  // Realistic scale
    seed: 141_421
)
```

### 3. Test Edge Cases

Try extreme but plausible scenarios:

```swift
// Test boundaries
_ = try recoveryCheck(trueA: 0.001, trueB: 0.001, trueSigma: 0.001, seed: 173_205)  // Near zero
_ = try recoveryCheck(trueA: 10.0, trueB: 10.0, trueSigma: 1.0, seed: 173_206)      // Large values

// Test high noise
_ = try recoveryCheck(trueA: 0.2, trueB: 0.3, trueSigma: 2.0, seed: 173_207)        // SNR << 1
```

### 4. Document Your Validation

Include validation results in your analysis documentation:

Record the seeds, so the run can be reproduced, and record what the pass rate *should* be —
a bare "pass rate: 100%" is a claim about the tolerance as much as about the model. These are
the actual figures from the replicate run in this guide:

## Relationship to Other Validation Methods

### Fake-Data Simulation vs. Cross-Validation

- **Fake-data**: Tests if fitting procedure works at all
- **Cross-validation**: Tests out-of-sample predictive performance
- **Use both**: Fake-data first (sanity check), then cross-validation (model selection)

### Fake-Data Simulation vs. Full SBC

- **Fake-data (this guide)**: Single draw from specific parameters
- **Full SBC**: Many draws from prior, check coverage statistics
- **Fake-data is**: Quicker, easier, catches most problems
- **Full SBC is**: More rigorous, required for publication-quality validation

## Common Questions

**Q: Do I really need this? My model is simple.**

A: Yes! Even simple models can have implementation bugs, numerical issues, or identification problems you didn't anticipate. It takes minutes to check.

**Q: The validation passed. Does that mean my model is good?**

A: No. It means your **fitting procedure works**. The model could still be inappropriate for your real data. You still need domain knowledge, residual diagnostics, predictive checking, etc.

**Q: The validation failed. What should I do?**

A: Investigate systematically:
1. **Ask whether it actually failed.** Compare the miss to the estimator's own standard
   error before you go looking for a bug. A single ✗ on `sigma` at `N = 100`, where the
   relative standard error is 7.1%, is expected roughly one run in six.
2. Re-run with several seeds. A defect fails on all of them; noise fails on some.
3. Check for coding bugs
4. Try different initializations
5. Increase iterations / adjust learning rate — and note that these are different fixes.
   Iterations help a fit that is still travelling; the learning rate is what to change when
   the fit is diverging.
6. Check if model is identified (can different parameters give same data?)
7. Try simpler model first
8. Examine optimization diagnostics — the parameters, not just the `converged` flag

**Q: How close should recovered parameters be to true parameters?**

A: Close to the estimator's sampling error, not to zero. A correct fit still misses, and the
size of the miss is predictable:

- Sample size: larger N → better recovery, as `1 / sqrt(N)`. For a residual standard
  deviation the relative standard error is about `1 / sqrt(2N)` — 15.8% at N = 20, 7.1% at
  N = 100, 5.0% at N = 200.
- Noise level (larger σ → worse recovery)
- Model complexity (more parameters → harder)
- Typical guideline: Within 10-20% relative error for moderate sample sizes — but pick the
  tolerance from the arithmetic above, not from habit. A 10% tolerance at N = 100 will fail
  about one run in six on `sigma` no matter how correct the code is, and a validation check
  that cries wolf at that rate stops being read.
