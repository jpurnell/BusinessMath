# Loading Financial Data from External Sources

Write an adapter that turns your source system's vocabulary into BusinessMath's typed values.

## Overview

BusinessMath does not read files. There is no CSV reader, no JSON schema, no connector for
your accounting package. What it has instead is a typed model — ``Entity``, ``Period``,
``TimeSeries``, ``Account`` and the three statements — that is `Codable` end to end, and a
role vocabulary that parses from strings for free.

The division of labour is worth stating plainly, because it determines where your code goes:

- **Your adapter** owns the file format, the source system's account names, the currency
  scale, and the decision about what to do with a row it does not recognise.
- **BusinessMath** owns validation and computation. Its initializers throw on the mistakes
  an adapter actually makes — an account with no role, an entity that does not match, a
  period the series is missing.

Everything below is about the seam between the two.

## The interchange format is already there

Because the whole graph conforms to `Codable`, JSON round-trips without any work on your
part. `Account<T>` is `Codable where T: Codable`, and ``IncomeStatement``, ``BalanceSheet``
and ``CashFlowStatement`` each encode their entity, periods and accounts.

```swift
let acme = Entity(id: "ACME", primaryType: .internal, name: "Acme Manufacturing")
let quarters = [
    Period.quarter(year: 2024, quarter: 1),
    Period.quarter(year: 2024, quarter: 2)
]

let productRevenue = try Account(
    entity: acme,
    name: "Product Revenue",
    incomeStatementRole: .productRevenue,
    timeSeries: TimeSeries(periods: quarters, values: [100_000.0, 110_000.0])
)

let encoder = JSONEncoder()
encoder.outputFormatting = [.prettyPrinted, .sortedKeys]

let accountData = try encoder.encode(productRevenue)
let restoredAccount = try JSONDecoder().decode(Account<Double>.self, from: accountData)
print(restoredAccount.incomeStatementRole == .productRevenue)   // true
```

A statement round-trips the same way, and recomputes its totals from the decoded accounts:

```swift
let statement = try IncomeStatement(entity: acme, periods: quarters, accounts: [productRevenue])
let statementData = try encoder.encode(statement)
let restoredStatement = try JSONDecoder().decode(IncomeStatement<Double>.self, from: statementData)
print(restoredStatement.totalRevenue[quarters[0]] ?? 0)         // 100000.0
```

### What that JSON actually looks like

This is the output of encoding `productRevenue` above — not a schema, but the real bytes:

```json
{
  "entity" : {
    "id" : "ACME",
    "identifiers" : [ ],
    "metadata" : { },
    "name" : "Acme Manufacturing",
    "primaryIdentifierType" : { "internal" : { } }
  },
  "incomeStatementRole" : "productRevenue",
  "name" : "Product Revenue",
  "timeSeries" : {
    "metadata" : { "name" : "" },
    "periods" : [
      { "date" : 725778000, "type" : 6 },
      { "date" : 733636800, "type" : 6 }
    ],
    "values" : [ 100000, 110000 ]
  }
}
```

Three things follow from that shape, and they are the reason this format is a wire format
rather than an authoring format:

- **``Period`` encodes structurally, not legibly.** `type: 6` is `PeriodType.quarterly`'s
  integer raw value; `date` is a `Date` in `JSONEncoder`'s default reference-date seconds.
  Neither is something you want a human editing. Use `.dateEncodingStrategy = .iso8601` if
  the JSON will be read by people — but then decode with the matching strategy.
- **Roles encode as their case names.** `"productRevenue"` is the raw value, which is why
  the next section works.
- **The entity is repeated inside every account.** Encoding a statement with fifty accounts
  writes the entity fifty-one times. That is fine for a cache and wasteful for a file format
  you control; if you control it, store the entity once and reattach it on load.

Use this format for BusinessMath talking to itself — caching a parsed model, moving a
statement between processes. For data arriving from somewhere else, write an adapter.

## Mapping your vocabulary onto roles

``IncomeStatementRole``, ``BalanceSheetRole`` and ``CashFlowRole`` are `String`-raw-valued
enums with no explicit raw values, so each case's raw value is its own name. They are also
`CaseIterable`. Parsing is therefore already written:

```swift
let parsedRole = IncomeStatementRole(rawValue: "researchAndDevelopment")
print(parsedRole == .researchAndDevelopment)                    // true
print(BalanceSheetRole(rawValue: "cashAndEquivalents") != nil)  // true
print(CashFlowRole(rawValue: "capitalExpenditures") != nil)     // true
```

Do not hand-write a `switch` from strings to cases. It is redundant on the day you write it
and wrong the day a case is added, and a stale copy is indistinguishable from a typo in the
source data.

Your real mapping problem is the other one: your source system does not say
`"researchAndDevelopment"`, it says `"R&D Expense"`. That table is yours to own, and it
should be an explicit dictionary rather than string munging:

```swift
let acmeVocabulary: [String: IncomeStatementRole] = [
    "R&D Expense": .researchAndDevelopment,
    "Sales & Marketing": .salesAndMarketing,
    "G&A": .generalAndAdministrative
]
```

### Report unknown labels; do not default them

When a label matches nothing, say so. ``FormulaEvaluator`` takes the same line — an unknown
account name throws `FormulaError.unknownAccount` rather than evaluating as zero, because a
silent zero produces a model that is wrong and looks fine.

```swift
enum SourceAdapterError: Error {
    case unknownIncomeStatementRole(label: String, row: Int)
    case missingValue(row: Int, column: Int)
    case nonNumericValue(String, row: Int)
}

func adapterRole(forLabel label: String, row: Int) throws -> IncomeStatementRole {
    if let mapped = acmeVocabulary[label] { return mapped }
    if let direct = IncomeStatementRole(rawValue: label) { return direct }
    throw SourceAdapterError.unknownIncomeStatementRole(label: label, row: row)
}
```

`CaseIterable` gives you a usable error message rather than a bare failure:

```swift
let revenueRoleNames = IncomeStatementRole.allCases
    .filter(\.isRevenue)
    .map(\.rawValue)
print("Revenue roles: \(revenueRoleNames.joined(separator: ", "))")
```

### The one mapping you must write by hand

``EntityIdentifierType`` is the exception. It is not `CaseIterable` and it is not
`RawRepresentable`, because `custom(String)` carries an associated value. So it genuinely
needs a switch:

```swift
func adapterIdentifierType(forLabel label: String) -> EntityIdentifierType {
    switch label {
    case "ticker": return .ticker
    case "cusip": return .cusip
    case "isin": return .isin
    case "lei": return .lei
    case "internal": return .internal
    case "taxId": return .taxId
    default: return .custom(label)
    }
}
```

The `default` here is not the silent-fallback anti-pattern above. `custom(String)` exists
precisely to carry an identifier scheme the library does not know about, so the unrecognised
label survives into the model instead of being discarded.

## Validate on load

Do not write your own consistency checks before you have looked at what the initializers
already enforce. ``Account`` rejects an empty name, an empty time series, and an account
with no role at all. The statement initializers reject accounts whose role is wrong for the
statement, whose entity differs, or whose series is missing any of the statement's periods.

```swift
let cash = try Account(
    entity: acme,
    name: "Cash",
    balanceSheetRole: .cashAndEquivalents,
    timeSeries: TimeSeries(periods: quarters, values: [50_000.0, 55_000.0])
)

do {
    _ = try IncomeStatement(entity: acme, periods: quarters, accounts: [cash])
} catch let error as FinancialModelError {
    print("Rejected on load: \(error)")   // accountMissingRole(statement:accountName:)
}
```

The cases worth catching by name are `FinancialModelError.accountMissingRole`,
`.entityMismatch(expected:found:accountName:)` and
`.periodMismatch(accountName:missing:)` — the last carries exactly which periods the
account was short, which is usually the answer to "why did the import fail".

For a balance sheet, add the accounting identity. ``BalanceSheet/validate(tolerance:)``
checks `Assets = Liabilities + Equity` for every period and throws
`BusinessMathError.inconsistentData(description:)` (E202) naming the offending period,
both sides, and the difference:

```swift
let retainedEarnings = try Account(
    entity: acme,
    name: "Retained Earnings",
    balanceSheetRole: .retainedEarnings,
    timeSeries: TimeSeries(periods: quarters, values: [50_000.0, 55_000.0])
)

let balanceSheet = try BalanceSheet(
    entity: acme,
    periods: quarters,
    accounts: [cash, retainedEarnings]
)
try balanceSheet.validate(tolerance: 0.01)
```

Run this at the edge, on import, where you can still name the source row. Running it later
tells you the model is inconsistent but not which file made it so.

## Practical notes

**Scale and sign.** Source exports are frequently in thousands or millions, and many present
expenses as positive magnitudes. Apply both corrections in the adapter, once, at parse time:

```swift
func adapterValues(_ raw: [String], scale: Double, row: Int) throws -> [Double] {
    try raw.enumerated().map { column, text in
        let trimmed = text.trimmingCharacters(in: .whitespaces)
        guard !trimmed.isEmpty else {
            throw SourceAdapterError.missingValue(row: row, column: column)
        }
        guard let value = Double(trimmed.replacingOccurrences(of: ",", with: "")) else {
            throw SourceAdapterError.nonNumericValue(trimmed, row: row)
        }
        return value * scale
    }
}
```

**Missing values.** An empty cell is not zero. Decide per account which it is — a period
before the account existed is arguably zero; a period the export truncated is not — and make
that decision in the adapter where the context exists. `TimeSeries` will happily hold a
`Double.nan`, and nothing downstream will warn you.

**Period alignment.** An account's series must cover every period the statement declares; it
may cover more. Build the period list once from the source and reuse it for every account
rather than deriving it per row, or you will get `periodMismatch` on the one account whose
column header was spelled differently.

**Provenance.** ``AccountMetadata`` already has fields for this — `externalId`,
`externalAccountType`, `externalDetailType`, `externalSourceSystem`. Fill them in during
import so that a surprising number six months later can be traced to a row in a file.

```swift
var importMetadata = AccountMetadata()
importMetadata.externalSourceSystem = "Acme ERP"
importMetadata.externalId = "4000-01"
importMetadata.externalAccountType = "Income"

let taggedRevenue = try Account(
    entity: acme,
    name: "Product Revenue",
    incomeStatementRole: .productRevenue,
    timeSeries: TimeSeries(periods: quarters, values: [100_000.0, 110_000.0]),
    metadata: importMetadata
)
print(taggedRevenue.metadata?.externalSourceSystem ?? "none")
```

## The shape of an adapter

A working adapter for a real accounting system tends to separate into three pieces, and the
separation is worth copying:

1. **A vocabulary** — the source system's own type taxonomy, modelled as its own enums, kept
   distinct from BusinessMath's roles. This is the part that changes when the vendor changes.
2. **A mapper** — rules from that vocabulary to ``IncomeStatementRole``,
   ``BalanceSheetRole`` and ``CashFlowRole``, returning `nil` or throwing for anything
   unrecognised so the caller decides.
3. **A normalizer or parser** — the format layer that turns a report payload or a CSV export
   into rows, then hands them to the mapper.

LedgeOS's QuickBooks plugin is one instance of this pattern, with a
`QuickBooksVocabulary`, a `QuickBooksMapper`, a `QuickBooksReportNormalizer` and a
`QuickBooksCSVParser`. It is a separate project and does not ship with BusinessMath; it is
named here only as an example of the shape, not as a dependency you can import.
