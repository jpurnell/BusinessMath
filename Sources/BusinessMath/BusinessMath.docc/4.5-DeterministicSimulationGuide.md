# Deterministic Simulation Guide

Make Monte Carlo runs reproducible with seeds, and run them without blocking using the async API.

## Overview

By default a Monte Carlo simulation draws fresh randomness on every run, so two runs
never produce the same numbers. That is correct for production risk analysis, but it
makes tests flaky and results impossible to reproduce in a bug report.

This guide covers the two features that fix that:

- **Seeding**: pass a `seed` to ``MonteCarloSimulation`` and the same configuration
  reproduces identical results on every run.
- **Async execution**: `run()` has an `async` overload that never blocks a thread
  while the GPU works, and honors task cancellation on the CPU path.

## Seeding a Simulation

Pass a seed at initialization (or set the ``MonteCarloSimulation/seed`` property):

```swift
var simulation = MonteCarloSimulation(iterations: 10_000, seed: 42) { inputs in
    inputs[0] - inputs[1]
}
simulation.addInput(SimulationInput(name: "Revenue",
    distribution: DistributionNormal(1_000_000, 100_000)))
simulation.addInput(SimulationInput(name: "Costs",
    distribution: DistributionNormal(700_000, 50_000)))

let first = try simulation.run()
let second = try simulation.run()
// first.values == second.values — identical, element for element
```

On the CPU path, every input samples through a ``SplitMix64`` generator initialized
with your seed. On the GPU path, the seed derives every thread's RNG state in the
Metal kernel. Both are fully reproducible.

### What determinism guarantees — and what it doesn't

Determinism is guaranteed **per execution path**:

- Same seed + same inputs + same iterations + same path (GPU or CPU) → identical results.
- A seeded **GPU** run and a seeded **CPU** run produce *different* (each internally
  reproducible) streams — they use different RNG algorithms.
- If GPU execution fails mid-run, the simulation falls back to the seeded CPU path
  and records the fallback in `SimulationResults.executionNotes`.

### Inputs must support seeding

Seeded runs require every input's distribution to conform to
``SeedableDistribution`` — all built-in distributions (Normal, Uniform, Triangular,
Exponential, LogNormal, Weibull, Logistic, Geometric, Pareto, ChiSquared, Gamma,
Beta, T, F, Rayleigh) do. Two configurations cannot honor a seed and **throw
`SimulationError.seedingUnsupported`** rather than silently losing determinism:

- Inputs built from a **custom sampler closure** (the closure owns its randomness).
- **Correlated sampling** (`correlationMatrix` / `runCorrelated`) — not yet seedable.

Check ``SimulationInput/supportsSeeding`` to test an input up front.

### Seeding custom distributions

Conform your distribution to ``SeedableDistribution`` by drawing *every* uniform
from the provided generator:

```swift
// Your distribution, conforming to `DistributionRandom` as usual. All of the
// distribution's math lives in one place: its inverse CDF (quantile function).
public struct MyDistribution: DistributionRandom {
    public let lower: Double
    public let upper: Double

    public func inverseCDF(_ p: Double) -> Double {
        lower + p * (upper - lower)
    }

    public func next() -> Double {
        inverseCDF(Double.random(in: 0...1))
    }
}

extension MyDistribution: SeedableDistribution {
    public func next<G: RandomNumberGenerator>(using generator: inout G) -> Double {
        // Same math as next(), but all randomness flows from `generator`
        inverseCDF(Double.random(in: 0...1, using: &generator))
    }
}
```

The seeded and unseeded paths must follow the same probability law — only the
randomness source differs.

## Async Execution

In an async context, `run()` automatically resolves to the async overload:

```swift
let results = try await simulation.run()
```

Prefer it there: the synchronous `run()` blocks its thread with
`waitUntilCompleted()` while the GPU works, which can starve Swift concurrency's
cooperative thread pool under load. The async overload:

- awaits GPU completion through a completion handler (no blocked thread),
- checks `Task.checkCancellation()` and yields every 1,024 CPU iterations, throwing
  `CancellationError` promptly when the surrounding task is cancelled,
- produces results identical to the sync overload for the same seed and path.

> Tip: To call the *synchronous* overload from an async context (rarely needed),
> wrap it in a synchronous helper function — a bare `run()` in async code always
> selects the async overload.

## Reproducible Tests

Seeds turn statistical assertions into exact ones. Drop this into a test target:

```swift
import Testing
@testable import BusinessMath

@Test func revenueModelIsStable() throws {
    var simulation = MonteCarloSimulation(iterations: 1_000, enableGPU: false, seed: 7) { $0[0] }
    simulation.addInput(SimulationInput(name: "X", distribution: DistributionNormal(100, 15)))

    let first = try simulation.run()
    let second = try simulation.run()

    // Deterministic: the same seed reproduces the stream element for element.
    #expect(first.values == second.values)
    #expect(abs(first.statistics.mean - 100) < 2)  // tight, non-flaky bound
}
```
