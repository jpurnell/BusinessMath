# Design Proposal: BusinessMath GPL Relaunch (Fresh Repo, 1.0)

**Objective:** Replace the existing MIT-licensed BusinessMath repository with a new GPLv3 + Commercial dual-licensed repository, starting at version 1.0.0. The new repo keeps the same name, GitHub URL, and module names. Pro-tier features are excluded from the public repo and live exclusively in BusinessMathPro.

**Master Plan Reference:** v3.0 protocol foundations are committed on current `main`; this proposal governs how they ship publicly under a new license and version scheme.

---

## 1. Rationale

BusinessMath is currently MIT-licensed with a single author (Justin Purnell) and no external contributors or adopters. The open-core model already separates free (BusinessMath) from premium (BusinessMathPro). Relaunching under GPLv3 creates a second revenue stream from proprietary commercial use of the base library.

A fresh repository (rather than a license change on the existing repo) provides:
- Clean GPL git history from commit 1 — no mixed-license archaeology
- Natural point to exclude Pro-tier files without rewriting history
- Unambiguous licensing story for auditors and commercial customers
- Clean 1.0.0 semver start aligned with the protocol-era architecture

| Path | Who pays | What they get |
|------|----------|---------------|
| GPLv3 (free) | Open-source projects, academics, researchers | Full BusinessMath, must open-source derivative works |
| Commercial license | Proprietary/fintech products | BusinessMath without copyleft obligations |
| BusinessMathPro | Institutional users | Premium features, includes commercial BusinessMath license |

**Why GPLv3 (not AGPLv3):** BusinessMath is a library consumed via SPM, not a network service. GPLv3's distribution trigger is the correct fit.

**Why now:** Sole authorship means no CLA/CAA negotiations. No existing proprietary adopters. Zero cost to try; trivially reversible.

| Package | Package.swift reference | Risk |

| **BusinessMathDemo** | `url: ".../BusinessMath", branch: "main"` | LOW — demo tools for core features |

## 11. Migration Sequence

### Phase 0: Backup (MANDATORY, fully reversible)

1. `git bundle create ~/BusinessMath-MIT-archive.bundle --all` — full git history backup
2. Archive `../BusinessMath/` directory to a safe location outside Dropbox
3. Note all current git tags: `git tag -l`
4. Export GitHub repo settings (description, topics, visibility)
5. Screenshot or note GitHub repo configuration (branch protection, webhooks, etc.)

**Rollback from Phase 0:** Delete archive files. No changes made.

### Phase 1: Prepare new repo locally (fully reversible)

1. Create temp directory: `../BusinessMath-GPL/`
2. `git init` with GPLv3 LICENSE as first commit
3. Copy all source files from `../BusinessMath/Sources/` **excluding** Pro-tier files
4. Copy all test files from `../BusinessMath/Tests/` **excluding** tests for Pro-tier files
5. Copy `Package.swift`, `CLAUDE.md`, `README.md` (with license updates)
6. Create `LICENSING.md`
7. Clone fresh `development-guidelines` and sync customizations
8. Run `swift build` — must succeed with zero errors
9. Run `swift test` — must pass (test count will be lower after Pro exclusions)
10. Document exact test count delta (current: ~4,944 → new: TBD)

**Rollback from Phase 1:** `rm -rf ../BusinessMath-GPL/`. Original repo untouched.

### Phase 2: Prepare Pro repo (fully reversible)

1. Copy excluded Pro-tier files into BusinessMathPro Sources
2. Copy excluded Pro-tier test files into BusinessMathPro Tests
3. Update BusinessMathPro's Package.swift if needed
4. Run `swift build` and `swift test` on BusinessMathPro
5. Verify BusinessMathPro tests that `import BusinessMath` still work against the new repo (point local path to `../BusinessMath-GPL/` temporarily)

**Rollback from Phase 2:** Revert BusinessMathPro changes. Original repos untouched.

### Phase 3: Verify all dependents (fully reversible)

For each of the 9 dependent packages, temporarily point their BusinessMath dependency at `../BusinessMath-GPL/` and verify they build:

1. BusinessMath-Adapters — update path, `swift build`
2. businessMathMCP (primary) — update path, `swift build`
3. businessMathMCP (legacy) — update path, `swift build`
4. BusinessMathDemo — update path, `swift build`
5. BusinessMath-Persistence — update path AND version pin, `swift build`
6. BusinessMathMarketData — update path, `swift build`
7. BusinessMathPro — already verified in Phase 2
8. BusinessMathCharts — re-resolve Xcode dependency
9. BusinessMathSample — update path, `swift build`
10. BusinessMathExplorer — verify playground builds

**Compile any failures into a punch list before proceeding.**

**Rollback from Phase 3:** Revert all Package.swift changes in dependents. Original repos untouched.

### Phase 4: Execute swap (PARTIALLY IRREVERSIBLE)

> **⚠️ POINT OF DECREASED REVERSIBILITY**
> Deleting the GitHub repo destroys stars, issues, and PR history.
> The git bundle from Phase 0 preserves code history but not GitHub metadata.

1. Rename local directory: `../BusinessMath/` → `../BusinessMath-MIT-frozen/`
2. Rename new directory: `../BusinessMath-GPL/` → `../BusinessMath/`
3. Delete old GitHub repo: `gh repo delete jpurnell/BusinessMath --yes`
4. Create new GitHub repo: `gh repo create jpurnell/BusinessMath --public`
5. Push new repo: `git remote add origin ... && git push -u origin main`
6. Tag: `git tag 1.0.0 && git push --tags`
7. Update all dependent Package.swift files to final references
8. Verify all dependents build against GitHub URL
9. Update BusinessMath-Adapters, businessMathMCP, etc. LICENSE files to GPLv3
10. Push all dependent repos

**Rollback from Phase 4 (partial):**
- Local code: rename directories back
- GitHub: recreate repo from bundle, but stars/issues/PRs are lost
- Dependent Package.swift files: revert changes

### Phase 5: Cleanup

1. Delete `../BusinessMath-MIT-frozen/` (only after confirming everything works)
2. Clear SPM caches on all dev machines: `rm -rf ~/Library/Caches/org.swift.swiftpm/`
3. Update `~/.claude.json` MCP config if paths changed
4. Update project memory files
5. Verify businessMathMCP server on roseclub.org still resolves dependency

## 12. Known Wrinkles

### W1: BusinessMath-Persistence version pin

**Problem:** Pins `from: "1.40.1"`. New repo starts at 1.0.0.
**Fix:** Update to `from: "1.0.0"` or `branch: "main"`.
**Risk:** LOW — simple Package.swift edit.

### W2: BusinessMathPro test imports of excluded types

**Problem:** Pro tests may `@testable import BusinessMath` and use types like StatementIntegration, HedgingProgram that are moving to Pro.
**Fix:** Change those imports to `@testable import BusinessMathPro` after the types move.
**Risk:** MEDIUM — requires identifying which test files reference excluded types.

### W3: Two businessMathMCP locations

**Problem:** Legacy location at `Development/Swift/businessMathMCP/` and primary at `Development/Swift/Playgrounds/Math/businessMathMCP/`. Both import BusinessMath.
**Fix:** Verify both build. Consider consolidating to one location during migration.
**Risk:** LOW — but easy to forget the legacy copy.

### W4: BusinessMathCharts Xcode project

**Problem:** Xcode project files store resolved dependency info differently than SPM. May require opening in Xcode and re-resolving.
**Fix:** Open project in Xcode, File → Packages → Reset Package Caches, rebuild.
**Risk:** LOW — but can't be automated.

### W5: Playground files in BusinessMathExplorer

**Problem:** Xcode Playgrounds may cache compiled frameworks. After repo swap, playgrounds may fail until caches are cleared.
**Fix:** Delete derived data for the playground workspace.
**Risk:** LOW — but annoying if forgotten.

### W6: roseclub.org deployment

**Problem:** The MCP server on roseclub.org depends on BusinessMath. After the GitHub repo is replaced, the server needs to re-resolve dependencies.
**Fix:** SSH into roseclub.org, clear SPM cache, rebuild.
**Risk:** MEDIUM — different Swift version (6.0.3 vs local 6.3). Must verify the new repo builds on 6.0.3.

### W7: development-guidelines sync

**Problem:** Current repo has extensive project-specific content in development-guidelines (master plan progress, completed proposals, session summaries). A fresh clone from the template repo won't have this.
**Fix:** After cloning fresh guidelines, copy over project-specific files from the archived repo's guidelines. Must be done carefully — template files should come from the fresh clone, project-specific files from the archive.
**Risk:** MEDIUM — risk of losing project history if files are missed. Create a checklist of all project-specific guideline files before migration.

### W8: GitHub metadata loss

**Problem:** Deleting the GitHub repo destroys stars, watchers, issues, PR history, and any inbound links.
**Fix:** None — this is inherent to repo deletion. Since there are no external users, the practical impact is minimal. But any bookmarked URLs to the old repo will 404 briefly until the new repo is created at the same URL.
**Risk:** LOW given zero external adoption. Would be HIGH if there were users.

### W9: Dropbox sync during migration

**Problem:** Renaming/moving directories inside Dropbox can cause sync conflicts if Dropbox is actively syncing.
**Fix:** Pause Dropbox sync before Phase 4 directory operations. Resume after completion.
**Risk:** MEDIUM — Dropbox sync has caused issues in this project before.

### W10: Test count delta

**Problem:** Removing Pro-tier files and their tests will reduce the test count. The exact delta is unknown until the excluded test files are identified.
**Fix:** Document the delta explicitly during Phase 1. Verify no non-Pro tests were accidentally excluded.
**Risk:** LOW — but the test count should be recorded for confidence.

## 13. Adversarial Review

**Strongest case for a different approach:**
Just change the LICENSE file on the existing repo and tag it v3.0. Same legal effect, zero blast radius, no dependent package updates needed, no risk of data loss. The "clean git history" argument is aesthetic, not legal — GPL applies from the commit where the LICENSE changes, regardless of prior history.

**Why we're not doing that:**
The existing repo has Pro-tier files committed on `main`. Removing them requires either reverting commits (messy history) or rewriting history (destructive). A fresh repo avoids both. The license change is the opportunity to also cleanly separate the public/private boundary — doing both at once is more work upfront but avoids a second migration later.

**Where this design is most likely wrong:**
The assumption that the migration can be executed atomically. In practice, there will be a window where the old repo is deleted but dependents haven't been updated, or the new repo is pushed but not all dependents have been verified. During this window, `swift build` will fail for any package that resolves BusinessMath from GitHub.

**Mitigation:** Phase 3 (verify all dependents) must be completed thoroughly before Phase 4 (execute swap). The swap itself should be done in a single focused session with all dependent repos ready to push.

**What an experienced critic would say:**
"You're engineering a complex multi-repo migration to solve a problem that a one-line LICENSE change would fix. The Pro-tier file separation is a separate concern that could be handled independently." This is fair. The counterargument is that doing both together means one disruption instead of two, and the fresh repo start aligns the version scheme (1.0) with the new licensing era. But if the migration proves too risky during Phase 3 verification, falling back to the simpler "change LICENSE + tag v3.0" approach is always available.
