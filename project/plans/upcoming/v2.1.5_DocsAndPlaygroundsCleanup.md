# BusinessMath v2.1.5 — DocC and Playgrounds `String(format:)` Cleanup

**Status:** DRAFT — held for future execution
**Target release:** v2.1.5 (patch — pure documentation/example cleanup, no compiled-code changes)
**Driver:** Complete the format-string rule enforcement across the entire BusinessMath codebase. Sources/, Tests/, and Examples/ are already clean as of v2.1.4. The remaining violations live in DocC documentation files (`Sources/BusinessMath/BusinessMath.docc/*.md`) and Xcode Playgrounds (`Playgrounds/**/*.swift`).

---

## 1. Objective

Remove every remaining `String(format:)` violation from BusinessMath's
non-compiled assets so the format-string rule is uniformly enforced across
the entire repository — not just the compiled package targets.

These violations don't crash anything because they're not compiled — DocC
markdown samples are static text, and the playground files are interpreted
in Xcode rather than built into the package. But they propagate the banned
pattern to anyone who:
- Reads the documentation and copies the example code into their own project
- Opens a playground to learn BusinessMath APIs
- Uses the playgrounds as templates for their own work

The compiled-code rule is meaningless if the documentation contradicts it.

## 3. Replacement patterns

The compiled-code cleanups in v2.1.3 / v2.1.4 standardized on these
patterns. Use the same rules for documentation and playgrounds:

### 3.1 Numeric formatting

```swift
// ❌ Before
String(format: "%.2f", value)
String(format: "%.4f%%", percentage * 100)
String(format: "%.0f", roundedValue)

// ✅ After
value.number(2)
"\((percentage * 100).number(4))%"
roundedValue.number(0)
```

The `.number(N)` extension is documented in `usage_examples.md` and is
already used throughout the now-clean Sources/ and Examples/.

### 3.2 String interpolation in print/println

```swift
// ❌ Before
print(String(format: "Result: %.3f (rate: %.1f%%)", value, rate * 100))

// ✅ After
print("Result: \(value.number(3)) (rate: \((rate * 100).number(1))%)")
```

### 3.3 Map operations

```swift
// ❌ Before
arr.map { String(format: "%.2f", $0) }

// ✅ After
arr.map { $0.number(2) }
```

### 3.4 Edge cases

- **Hexadecimal formatting** like `String(format: "%02x", byte)`: replace with `String(byte, radix: 16, uppercase: false)` followed by manual `"0"` prefix if length < 2 (the same pattern that `TemplateRegistry.swift` got in v2.1.3).
- **Width-padded integer columns** like `String(format: "%10d", n)`: use `String(n).padding(toLength: 10, withPad: " ", startingAt: 0)` (or for right-aligned, prepend spaces manually).
- **Multi-arg format strings** like `String(format: "%@%.2f%@%.2f", a, b, c, d)`: rewrite as straightforward string interpolation. The `%@` placeholder is for objects, but since these are all strings/numbers in playgrounds, interpolation is the right answer.

## 4. Execution plan

### 4.1 Order of operations

Recommended order to keep diffs reviewable and isolate any issues:

1. **DocC files first** (~62 instances, 12 files). Pure markdown text edits, zero compile risk. Verify with `swift package generate-documentation` after each batch (or at the end).

2. **`Playgrounds/BusinessMath Example Playgrounds/` next** (~14 files, ~120 instances). These are the playgrounds users open from the README and tutorials. Highest visibility.

3. **`Playgrounds/Blog/`** (~5 files, ~20 instances). Lower priority — these are blog post draft files for content marketing, not API tutorials.

4. **`Playgrounds/N02_tue_gpu_acceleration.playground`** (~2 instances). Standalone, do last or first, doesn't matter.

### 4.2 Per-file workflow

For each file:
1. Read the full file
2. Find all `String(format:` occurrences with grep
3. Apply the replacement patterns from §3
4. Verify the file still parses (for playgrounds: open in Xcode, run; for DocC: `swift package generate-documentation`)
5. Stage the file

### 4.3 Verification

After all files are cleaned:

```bash
# Should produce zero output
grep -rln 'String(format:' --include='*.swift' Playgrounds/
grep -rln 'String(format:' --include='*.md' Sources/BusinessMath/BusinessMath.docc/

# Run the existing tests to confirm nothing else changed
swift test
```

**Playground sanity check:** open at least 2-3 of the cleaned playgrounds in Xcode and run them end-to-end. The interpreter is more permissive than the package compiler, so a syntactically-valid `.swift` file may still produce wrong output if the replacement formula is subtly wrong (e.g., locale-dependent thousands separators showing up where they didn't before). The most common failure mode: `value.number(N)` adds thousands separators (`1,234.56`) where `String(format: "%.2f", value)` did not (`1234.56`). For playgrounds with assertion-style "expected output" comments, this matters.

### 4.4 Locale-neutral alternatives if `value.number(N)` produces unwanted grouping

If a playground specifically needs no thousands separators (matching original `printf` semantics), use the verbose form:

```swift
value.number(2, .toNearestOrAwayFromZero, .init(identifier: "en_US_POSIX"), .automatic, .never, .automatic)
```

The `.never` argument disables grouping. This is the same pattern that
`FloatingPointFormatter.swift` uses internally via its private helper.

For most playground output, the thousands separator difference is cosmetic
and acceptable. Only worry about it if a specific playground shows
`-100,000.00` style values where users would have grown used to `-100000.00`.

## 7. Why this is held, not active

Two reasons:

1. **Doesn't block anything.** The compiled code is already format-string-clean. The DocC and playground violations don't trigger build errors, don't fail CI, and don't propagate to runtime crashes. They only bother people reading the docs.

2. **The downstream BioFeedbackKit work in narbis is the higher priority.** Per the v2.1.3 / v2.1.4 session summaries and the narbis handover at `narbis/project/summaries/2026-04-07_BusinessMathTriple_Handover.md`, the user is working through commercial biofeedback features and BusinessMath upstream work is supporting infrastructure. Six hours of mechanical doc cleanup is six hours not spent on FrequencyDomainMetrics.

When this work IS picked up, it should be done as a single atomic PR (one commit, all files, single CHANGELOG entry, single tag) to keep the release cadence clean.
