# v2.7.0 — Additive Sizing Fixes and Safe Determinism

**Status:** Scoped, ready to build
**Created:** 2026-08-23
**Why this exists:** `proposals/MarketingLeg.md` §2.4 found a shipped defect in
`sampleSize`. §12.1 of that proposal argued the fix must not wait for the major, and
adversarial review agreed. This is that release.

---

## 1. The argument for shipping this separately

`sampleSize` returns a number **4.1× too small** for its documented purpose, today, in
users' hands. `v3.0.0_SCOPE.md` gathers everything waiting on a major, and the marketing
leg proposed alongside it is a substantial body of work. Holding a live mathematical defect
behind a feature programme is indefensible when the fix is purely additive.

It is also what this project's own rules already say. `v3.0.0_SCOPE.md` §3:

> Anything in `upcoming/` that is additive. New capability does not need a major and
> should not wait for one.

**Everything in this release is additive.** No signature changes, no deletions, no
behaviour changes to existing calls.

## 2. The correct sizing calculation

### 2.1 What is wrong

`AB Test.swift` documents `sampleSize(ci:proportion:n:error:)` as *"the minimum number of
observations for each variant of an A/B test."* The body is Cochran's finite-population
**survey** formula — `z²pq/e²` with a finite-population correction — which is missing
everything a two-arm power calculation needs: no `z_β`, so it cannot express power at all;
no second arm's variance; and `error` is a margin of error around one proportion rather
than a difference to detect.

The parameter documentation discusses surveys, population size, and "the researcher." The
formula is correct for what its parameters describe and wrong for what its summary claims.

| At 95% confidence, p = 0.5, e = 0.05, large population | Per arm |
|---|---|
| What `sampleSize` returns | **384** |
| Correct two-proportion sizing, 80% power, detecting 0.50 → 0.55 | **1,565** |
| Understated by | **4.1×** |

Reproducible against R's `power.prop.test(p1 = 0.50, p2 = 0.55, power = 0.80)`.

### 2.2 New area: `Statistics/Experiment/`

Domain-neutral, per the placement rule in `MarketingLeg.md` §3.1 — experiment design is
used in medicine, agriculture, and product analytics, not only marketing. Marketing
consumes it in 3.0.0; nothing here depends on the marketing work.

```
Statistics/Experiment/
    Experiment.swift          Design: arms, baseline, minimum detectable effect
    PowerAnalysis.swift       Two-proportion and two-mean sizing; achieved power; MDE
    EffectSize.swift          Absolute and relative lift with confidence intervals
```

```swift
public struct Experiment<T: Real & Sendable>: Sendable {
    public static func twoProportion(baseline: T, minimumDetectableEffect: T) -> Experiment
    public static func twoMean(baseline: T, standardDeviation: T,
                               minimumDetectableEffect: T) -> Experiment

    public func sampleSizePerArm(power: T, alpha: T, tails: Tails) throws -> Int
    public func achievedPower(perArm: Int, alpha: T, tails: Tails) throws -> T
    public func minimumDetectableEffect(perArm: Int, power: T, alpha: T) throws -> T

    public func analyze(_ observed: ArmResults<T>) throws -> ExperimentResult<T>
}

public struct ExperimentResult<T: Real & Sendable>: Sendable {
    public let absoluteLift: T
    public let relativeLift: T
    public let interval: ClosedRange<T>    // the answer
    public let pValue: T                   // the footnote
}
```

`analyze` returns an effect size with an interval because *"is it significant"* and
*"is it worth shipping"* are different questions and only the interval answers the second.

**Throwing, not clamping.** A power of 0 or 1, a non-positive MDE, an alpha outside (0,1),
or a baseline outside [0,1] have no correct answer. Returning a plausible integer for a
nonsensical design is the same class of failure this release exists to fix.

### 2.3 Deprecating `sampleSize`

```swift
@available(*, deprecated, message: "Use Experiment.sampleSizePerArm(power:alpha:tails:) instead. The legacy formula understates required sample size for two-arm A/B tests by ~4.1x.")
public func sampleSize<T: Real>(ci: T, proportion p: T, n: T, error: T) -> T
```

The message names **the defect**, not merely the replacement. A user who reads only the
warning should learn that their past tests were undersized — that is the whole point of
shipping this now rather than quietly adding a better function beside it.

The function is **deleted in 3.0.0**, per `v3.0.0_SCOPE.md`.

**One honesty note on "non-breaking":** adding `@available(*, deprecated)` is
source-compatible — it emits a warning, not an error. But a downstream consumer building
with warnings-as-errors will fail to compile, and this project's own standard is zero
warnings, so its sibling packages plausibly do exactly that. The release notes should say
so, and `BusinessMath-Adapters`, `businessMathMCP`, and `BusinessMathMarketData` should be
checked before tagging rather than after.

### 2.4 A second defect in the same file, found during the RED phase

**This corrects an earlier claim in this document that `pValue` was correct and could stay
as-is. It is not, and it cannot.**

```swift
let zScore = abs(zScoreNum / zScoreDen)
let pValue = normSDist(zScore: zScore)
return pValue
```

`normSDist` is the standard normal **CDF**. The function therefore returns `Φ(|z|)`, which
is `1 − oneSidedP` — the complement of a p-value, not a p-value.

Because the code takes `abs(z)`, **the return value is always at least 0.5.** The test its
own documentation prescribes —

> `p < 0.05`: Statistically significant difference (95% confidence)

— **can never be true.** The function is structurally incapable of reporting significance.

Its documented worked example makes this concrete. For 120/1000 against 145/1000 the
documentation claims:

```swift
// Output: p-value: 0.043 (statistically significant at 95% level)
```

| Quantity | Value |
|---|---|
| What the code returns | **0.950526** |
| What the documentation claims | **0.043** |
| The true two-sided p-value | **0.098948** |
| The true one-sided p-value | 0.049474 |

Three different numbers, and the true two-sided result is **not significant** — so the
example's parenthetical is wrong even about its own conclusion.

**Why this is worse than the `sampleSize` defect.** An undersized test fails to reach
significance and reads as "no difference," which at least errs toward inaction. This
function returns a number that looks like a p-value, sits in the right range, moves in the
right direction as evidence accumulates, and is wrong by construction. A user who
tests `> 0.95` gets a **one-sided** test at α = 0.05 and does not know it.

**Treatment, identical to `sampleSize`:**

- **2.7.0:** deprecate, with a message naming the defect. Correct the doc comment in place —
  the example output is wrong regardless of what happens to the function.
  ```swift
  @available(*, deprecated, message: "Use Experiment.analyze(_:alpha:) instead. This function returns normSDist(|z|) — the complement of a one-sided p-value — not a p-value. It is always >= 0.5, so the documented `p < 0.05` test can never be true.")
  ```
- **3.0.0:** deleted alongside `sampleSize`.

The behaviour is **not** corrected in place. Changing what the function returns would be a
silent behaviour change for every existing caller — worse than a compile error, and exactly
the failure mode this release exists to remove.

### 2.5 Why both escaped

Neither defect is subtle once looked at, and both survived years of a rigorous quality gate.
The reason is the same in both cases and is worth recording:

- **`sampleSize` had no executable example**, so there was nothing for `doc-code` to check.
  Prose is unverifiable, and its summary line contradicted its own parameter list.
- **`pValue` had an example, but its claimed output is a comment, not an assertion.**
  Verifying that a documented figure matches what the code computes is `doc-claims` — rung
  3 — which is opt-in and not enabled here.
- **And the unit tests pinned the wrong behaviour under right-sounding names.** This is the
  part worth dwelling on, because it is the reason a green suite meant nothing.

  `testPValueDetailed` read:

  ```swift
  let resultSignificant: Double = pValue(obsA: obs, convA: convA, obsB: obs, convB: convSig)
  #expect(abs(resultSignificant - 0.9504) < 0.0001)
  ```

  The value asserted is the complement, and the case named `resultSignificant` has a true
  two-sided p of **0.0993** — not significant at all. A reader scanning the suite sees a
  variable called "significant" holding 0.95 and moves on. The test encoded the inversion
  and made it look deliberate.

  The second test asserted only:

  ```swift
  #expect(result > 0.0)
  #expect(result < 1.0)
  ```

  which cannot fail for any probability-like output. That is precisely the pattern
  `CLAUDE.md` forbids — *"assertions: use specific expected values, not `!= 0` or
  `!= nil`"* — and it is the clearest single reason the defect survived a rigorous gate:
  **the checker enforcing that rule cannot see inside an `#expect`.**

  Both tests are corrected in this release: renamed to say what they measure, and the true
  two-sided p-values asserted alongside the pinned legacy values, so the gap between what
  the function returns and what it should return is visible in the suite rather than only
  in these release notes.

`MarketingLeg.md` §16's two module-wide rules follow directly, and §4 below applies them.
**Enabling `doc-claims` on this package is worth its own consideration**: it is the checker
that would have caught this, and the reason it is opt-in is that arriving red means
remediation work, not that the rule is optional.

## 3. Determinism: keep the interim, deliberately

2.6.0 shipped an interim guard: `DifferentialEvolution` and `ParticleSwarmOptimization`
**decline the GPU when seeded**, executing deterministically on the CPU, because their
`optimizeDetailed` cannot throw.

**That guard stays in 2.7.0 exactly as shipped.** Removing it requires the throwing
signature, which is breaking, which is 3.0.0's first spine.

This is worth stating explicitly because the interim looks like something to clean up. It
is not: it is a correct trade that buys determinism at the cost of GPU acceleration on
seeded runs, and it holds the line until the signature can change. The release notes should
describe it as a deliberate constraint with a known end date, so it is not mistaken for an
oversight and "fixed" by someone restoring the silent fallback.

## 4. Documentation

Per `MarketingLeg.md` §16, arising from how this defect survived: **prose is unverifiable
and this function had no executable example.** The checkers verify that documented examples
produce their claimed values; they cannot verify that a summary line describes the formula
beneath it.

- Every function in `Statistics/Experiment/` ships an executable example with a checked
  numeric result. Not optional.
- `ExperimentDesignGuide.md` (DocC): sizing, stopping, and reading a result. It states
  plainly that `sampleSize` was wrong, by how much, and what to do about tests already run.
- `sampleSize`'s own documentation is corrected in place — the deprecation warning is not a
  substitute for the doc comment still describing a survey formula as an A/B calculation.

## 5. Test strategy

**Reference truth:** R's `power.prop.test` and `power.t.test`; G*Power for a second
independent check on the two-proportion case.

**Validation trace (becomes the golden-path assertions):**
- `power.prop.test(p1 = 0.50, p2 = 0.55, power = 0.80, sig.level = 0.05)` → **1,565 per arm**
- The same design's `achievedPower(perArm: 1565, ...)` → **0.80** (round-trip)
- `sampleSize(ci: 0.95, proportion: 0.5, n: 1e9, error: 0.05)` → **384.145735**, asserted so
  the deprecated function's *existing* behaviour is pinned rather than accidentally changed
- `pValue(obsA: 1000, convA: 120, obsB: 1000, convB: 145)` → **0.950526**, pinned for the
  same reason, with the true two-sided value **0.098948** asserted beside it so §2.4's
  defect is tested rather than merely described

**Properties:**
- Round-trip: size for (MDE, power) → compute achieved power at that n → returns the
  requested power
- Monotonicity: smaller MDE requires larger n; higher power requires larger n; larger alpha
  requires smaller n
- The interval from `analyze` contains the point estimate, and excludes zero exactly when
  the p-value is below alpha

**Refusals:** power ≤ 0 or ≥ 1; alpha outside (0,1); MDE ≤ 0; baseline outside [0,1]; zero
observations in an arm. Each asserts the specific error case.

## 7. Open questions

1. **Does `Statistics/Experiment/` want a `Tails` enum, or is one-sided testing a trap
   worth refusing?** One-sided tests are widely misused in A/B testing to manufacture
   significance. Offering the option is honest; defaulting to two-sided and documenting why
   is probably right.
2. **Should `analyze` warn on a sample smaller than the design called for?** It has the
   design and the observed n, so it can tell. That is arguably the single most useful thing
   this API could do for a user who inherited an undersized test.
3. **Do the sibling packages break on the deprecation warning?** §2.3. Needs checking
   before tagging.
