# v3.0.0 — Consolidated Scope

**Status:** Draft for pruning
**Last Updated:** 2026-08-12
**Why this exists:** 2.6.0 turned up a fix that can only ship as a breaking change. Rather
than let one item force a major on its own, this gathers everything already waiting on a
major so the break happens once.

---

## 1. The spine: determinism across every GPU path

Four plans that arrived separately turn out to be the same problem, which is the argument
for doing them together rather than one per release.

A GPU path that consumes randomness, fails, and falls back to the CPU returns a different
answer under a seed that promised otherwise. It presents as an occasional red suite rather
than a bug, because it needs GPU resource pressure to trigger — so it reproduces under a
full parallel run and never in isolation. It has now been found three times, in three
subsystems, by three separate investigations that did not recognise each other.

| item | source | state |
|---|---|---|
| DE/PSO `optimizeDetailed` → `throws` | `proposals/GPUAttemptSeedContract.md` §4 | **new, this is what forces the major** |
| Monte Carlo seeding + non-blocking GPU wait | `upcoming/MonteCarloDeterminismAndAsyncExecution.md` | PROPOSED |
| GPU buffer caching | `upcoming/gpuBufferCachingPlan.md` | Deferred, explicitly "correctness fixes first" |
| `commandBuffer.status` checks in remaining GPU paths | this session | GA done; others outstanding |

### 1.1 What 2.6.0 already shipped

The non-breaking half is done and released, so 3.0.0 starts from a working contract
rather than from the defect:

- `GPUAttempt.swift` — `RNGWrapper.attemptGPU(seeded:_:)` and `GPUAttemptOutcome`, which
  own the rewind and force each call site to state what it does when the seed promise
  cannot be kept. Adopted by `GeneticAlgorithm`.
- `GeneticAlgorithm` throws rather than substituting the CPU on a seeded run, including
  from the command-buffer guard that previously returned `nil` and fell back silently.
- `GeneticAlgorithm` checks `commandBuffer.status` after `waitUntilCompleted()`. No GPU
  path in the library had been doing this, so a failed dispatch was read out of the shared
  buffer as though it had succeeded.
- `DifferentialEvolution` and `ParticleSwarmOptimization` decline the GPU when seeded —
  the interim, because their `optimizeDetailed` cannot throw.

### 1.2 What 3.0.0 does

1. `DifferentialEvolution.optimizeDetailed` and
   `ParticleSwarmOptimization.optimizeDetailed` become `throws`, and both adopt
   `attemptGPU`. **Source-breaking: every call site needs `try`.** 67 in-repo call sites
   plus five DocC tutorials.
2. Delete the seeded-GPU guard added in 2.6.0. GPU and seed work together again, with
   refusal replacing silence. The interim leaves no API behind to deprecate — this is
   why it was chosen over adding a `usedCPUFallback` flag.
3. `commandBuffer.status` checked in `MonteCarloGPUDevice` and `MetalMatrixBackend`, and
   both audited against the `attemptGPU` contract. Neither is currently known to draw
   from a seeded generator before failing; that should be verified rather than assumed.
4. Monte Carlo determinism per its own plan — `MonteCarloSimulation` never exposes the
   `seed:` that `MonteCarloGPUDevice.runSimulation` already accepts.
5. GPU buffer caching, whose deferral condition ("correctness fixes first") is met by the
   above and not before.

## 1.3 A second instance of the same API problem

`EnterpriseValueBridge.valuePerShare(sharesOutstanding:)` is **non-throwing**, and divides
by a share count it does not check. Zero shares returns infinity; a negative count returns a
negative share price, which is worse because it looks like an answer.

The other three spellings of `valuePerShare` were repairable in 2.6.0 — `DividendDiscountModel`
already guarded, and `ResidualIncomeModel` and `FCFEModel` were declared `throws` while never
throwing, so adding the guard changed nothing about their signatures. This one cannot be fixed
the same way for exactly the reason DE and PSO cannot: the signature has no way to refuse.

Same decision, same release. Make it `throws` and guard it, alongside `optimizeDetailed`.

## 1.4 The seed contract is discarded one layer up, by composition

`IslandModel` composes `GeneticAlgorithm`, and swallows the throw that §1.1 added:

```swift
// IslandModel.swift:278
let result = try? island.minimize(objectiveFn, from: bestSolution) // silent: island failure treated as non-improvement
let fitness = result?.value ?? V.Scalar.infinity
```

`GeneticAlgorithm` throws on a seeded run whose GPU attempt fails, precisely so the caller
cannot receive a CPU answer under a seed that promised otherwise. `try?` turns that refusal
back into silence, and the island is then recorded as having found nothing.

**It is reachable, not theoretical.** Each island is built with
`populationSize: gaConfig.populationSize` — the *full* population, not a share of it — so a
run configured at 1000 or more puts every island on the GPU. And islands are seeded
explicitly (`seed: baseSeed &+ UInt64(i * 1000)`), which is the only condition under which
`GeneticAlgorithm` throws at all. So a seeded `IslandModel` run under transient GPU pressure
drops whichever islands failed, silently, and returns a different answer for the same seed.

The `// silent:` marker means the gate accepts it. The marker is honest about *what* the code
does and was written before the throw it now swallows existed.

`optimizeDetailed` is non-throwing here too, so this cannot be repaired without the same
signature change as §1.1 and §1.3. Note `minimize(_:from:constraints:)` *does* throw and
calls `optimizeDetailed` internally, so a partial repair is possible sooner if wanted — but
the three cases share one cause and should share one fix.

**Three instances now, in three subsystems: `optimizeDetailed` (DE, PSO, IslandModel),
`valuePerShare` (EnterpriseValueBridge), and this.** Each is a place where the correct
behaviour is refusal and the signature has no way to refuse. That is the argument for the
major, more than any single one of them.

## 4. Open questions

1. **Does `minimize(_:from:constraints:)` change too?** It already throws, so its
   signature is unaffected — but it currently calls `optimizeDetailed` and would begin
   propagating a new error case. That is a behaviour change for callers who catch
   specific errors, and it should be documented as such even though it compiles.
2. **Is there a deprecation path worth offering?** A non-throwing
   `optimizeDetailedUnchecked` would ease migration and re-introduce exactly the silent
   fallback the major exists to remove. Recommend not offering one, and saying why in the
   release notes.
3. **What is the version story for the sibling packages?** BusinessMath-Adapters,
   businessMathMCP, and BusinessMathMarketData all track this library and will need the
   `try` additions. Their bumps should be planned with 3.0.0, not discovered after it.
