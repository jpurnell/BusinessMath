### 1. Examples/ String(format:) cleanup

Both example files had ~40 combined `String(format:)` violations:

- `Examples/MultipleLinearRegressionExample.swift` — 22 calls
- `Examples/LinearRegressionConvenienceExample.swift` — 18 calls

All replaced with `value.number(N)` interpolation. Examples aren't part
of the package build target so these violations didn't fail CI before,
but they were user-facing reference code that propagated the banned
pattern to anyone copying from them.

### 2. `generateRandomReturns` seeded overload

The function in `Sources/BusinessMath/Portfolio/PortfolioUtilities.swift`
was using unseeded `Double.random(in:)`, violating the deterministic-
randomness rule. The v2.1.3 fix bypassed this in the failing test by
inlining Box-Muller with a seeded RNG, but the production function
itself was still wrong.

**Fix:**

- Added `generateRandomReturns(count:mean:stdDev:using: inout some RandomNumberGenerator)` overload
- Existing unseeded `generateRandomReturns(count:mean:stdDev:)` is now a thin wrapper that creates a `SystemRandomNumberGenerator` and calls the new overload
- Same observable behavior for existing callers — no breaking change
- Bonus: fixed an edge case where `Double.random(in: 0.0...1.0)` returning exactly 0 would cause `log(0) = -inf` in the Box-Muller transform; guarded with `Double.leastNormalMagnitude`

### 3. SeededRNG consolidation across 5 test files

5 test files had each declared a local `struct SeededRNG { var state: UInt64; ... }`
with the MMIX LCG (multiplier `6364136223846793005`):

- `Tests/BusinessMathTests/Statistics Tests/Descriptor Tests/Descriptives Tests.swift`
- `Tests/BusinessMathTests/Statistics Tests/Descriptor Tests/Dispersion Around the Mean Tests/Dispersion Around the Mean Tests.swift`
- `Tests/BusinessMathTests/Statistics Tests/Regression Tests/LinearRegressionConvenienceTests.swift`
- `Tests/BusinessMathTests/Statistics Tests/Regression Tests/DenseMatrixTests.swift`
- `Tests/BusinessMathTests/Statistics Tests/NonlinearRegressionTests.swift`

This was a different LCG from `TestSupport.SeededRNG` (which uses
Numerical Recipes constants). Consolidating naively to TestSupport would
have changed the random sequence and broken the tests' deterministic
assertions.

**Fix:**

- Added `TestSupport.MMIXSeededRNG` — a NEW value-type struct with the MMIX LCG, separate from the existing `TestSupport.SeededRNG`
- API: `init(state: UInt64 = 12345)`, `mutating func next() -> Double` (returns `[0, 1]`), `mutating func nextSigned() -> Double` (returns `[-1, 1]`)
- The `nextSigned()` variant matches the `[-1, 1]` mapping that `DenseMatrixTests` was doing inline
- All 5 affected files updated to remove their local struct declaration and use `MMIXSeededRNG` from TestSupport
- 2 files needed `import TestSupport` added (`Descriptives Tests.swift` and `DenseMatrixTests.swift` weren't importing it)
- **Bit-identical sequences preserved** — same LCG constants, same seed handling, no test assertions needed re-tuning

Net change: removed 5 duplicated struct declarations, added 1 canonical
declaration in TestSupport, gained `nextSigned()` for the [-1, 1] case.

## Context Loss Warnings

For the next session:

- **TestSupport now exports TWO seeded RNGs.** Use `SeededRNG`
  (Numerical Recipes LCG, class) for new tests where reproducibility is
  the only requirement. Use `MMIXSeededRNG` (MMIX LCG, struct) only
  when porting from older tests that need the bit-exact MMIX sequence.
  The two are NOT interchangeable — they produce different sequences
  for the same seed.
- **`generateRandomReturns` has two overloads now.** Production code
  should use the seeded variant (`using:`) when reproducibility matters.
  The unseeded variant is a convenience wrapper for "I just need some
  random numbers and don't care about reproducibility."
- **DocC samples still violate the format-string rule.** When updating
  documentation in the `.docc` folder, use `value.number(N)` not
  `String(format:)`. Lock this in for future doc edits.
