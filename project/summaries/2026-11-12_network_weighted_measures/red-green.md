# Red then green: weighted graph measures (step 2)

Branch `feature/network-weighted-measures`, stacked on `feature/network-values-protocol`.

## Method

1. Compile-stub first: `Centrality`, `Community`, `Brokerage` and the three `IndependentImplementations`
   oracles with the real public signatures and wrong behaviour. Every measure returns a right-sized result
   (a score of 0.0 for every node, every node in community 0, modularity 0, convergence report
   `(0, false, 0)`), so tests fail on assertions instead of trapping on a missing key or an index.
   The stub built clean (no compile errors, no warnings from the stub).
2. The ported suites (mutation audits, reference values, Burt, convergence, cross-checks), the new
   unweighted/weighted cross-check and the golden bit-for-bit test were run against the stub.
3. The real code was copied in (`WeightedCentrality.swift`, `WeightedCommunity.swift`,
   `BurtConstraint.swift`, and the oracles in `Tests/TestSupport`); same command, green.

Command: `swift test --filter "<suite names>"` (the filter is the regex of every new suite name; it
also matches a few pre-existing suites with the same words, noted below).

Golden values: `GoldenMeasureData.swift` was generated by a scratch program outside both repos
(`/private/tmp/claude-501/golden2`, depending on SwiftGraphMetrics by path), kept here as `golden/`.

## Red (stub): 192 tests in 23 suites, 55 passed, 137 failed, 4,577 issues

Every failure is a failed assertion (the run completed; nothing trapped). Representative failures:
the golden test fails on all 19 fixtures; `Eigenvector...` tests see zeros where hand-derived values
are expected; every Burt hand-derived value, the kite/karate published values, Louvain/k-core/
component expectations and the cross-check agreement tests fail.

## Green (real code): 194 tests in 23 suites passed, 2 known issues

`Test run with 194 tests in 23 suites passed after 2.269 seconds with 2 known issues.`
The two known issues are the two expectations of `louvainTieRuleFinding` (see the cross-check finding in
the summary and CHANGELOG). Before the fixture was split out, the same cross-check failed on `random3`
(partitions and modularity differ); the red run of that test against the real code is recorded here
because it was a real behavioural failure, not a stub artefact: `Set(plain) == asSets(weighted)` false,
`abs(plainQ - weightedQ) = 0.00458` on `random3`.

Two of my own expectations were wrong and were corrected against the real code, not the other way
round: the eigenvector scores of non-dominant components are near zero (3.5e-12 for an isolate at the
default 200 passes), not exactly zero, and two components with the same leading eigenvalue (two
triangles) both score one. The doc comments and ADR-007 say so.
